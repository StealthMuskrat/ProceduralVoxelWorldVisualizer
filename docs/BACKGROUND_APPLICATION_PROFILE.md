# Background Application Profile Apply

Development implementation on main; **uncompiled and untested** under the owner's testing pause. No compiler, Gradle, JUnit, native probe, consumer, Python/schema checker or GitHub workflow ran. The last observed baseline remains **922 tests / 120 suites**. This source coverage is not full Trees 2.3–2.4/4.4/19.6, A11/A22/A32/A33, Windows 11 or final release acceptance evidence.

## Worker preparation and activation

Production Application Settings uses the existing bounded editor executor. Explicit Apply captures complete private metadata and raw creation input, then workers reconstruct a separate candidate, validate registry ranges and cross-default/compiler compatibility, prepare its next private editing state, serialize it and force a private sibling file. Production no longer performs full metadata/compiler validation on every edited frame. Cheap per-control parsing/range feedback remains inline; cross-default errors appear from explicit Apply. Direct ApplicationSettingsPanel and MetadataEditSession.apply callers retain synchronous behavior.

Active labels, Help and creation defaults remain available during preparation. UI delivery only makes the private prepared file ready. The settings panel processes Escape, Cancel Apply, Revert and Stage Built-In Profile before its final action decision. A successful request completes from the original Apply action; it does not require a second confirmation. Apply/Cancel Apply widget identity includes the request version; Revert and Built-In actions retain their opening identity across worker delivery.

Final publication rechecks active metadata identity and complete values, the exact private draft/ledger/session revision, draft values, captured raw strings and current displayed input. Numeric-equivalent raw changes still retire work. Merely inspecting an additional unchanged canonical raw field may add a buffer without cancelling Apply. Replacing/reverting/staging the private draft or replacing/mutating the active profile prevents an older result from publishing. Changed active metadata requires Revert before another Apply; no implicit merge is performed.

After the final gate, the owner performs the existing required atomic replacement. Only then does it install exactly the prepared active metadata and prebuilt next editing state. No validation, copying or user callback lies between successful replacement and activation. No accepted cleanup unlinks a reused temporary pathname. Filesystem replacement itself remains owner-thread I/O; staging is not a promise of hard UI latency bounds on an arbitrary provider.

## Cancellation, recovery and domains

Cancel Apply and Escape retain the private profile and exact raw corrections. Edits retire pending work; Revert and Stage Built-In Profile explicitly replace the private draft. Leaving Application Settings, closing/collapsing its window, or shutting down cancels pending Apply without discarding the retained profile. A worker finishing after retirement owns disposal of its unpublished file. Queued/duplicate callbacks cannot publish into a successor. Cleanup failures produce a separate bounded APPLICATION_PROFILE_CLEANUP_FAILED event and cannot strand the next action; failed unlink is terminal for that pathname rather than an unsafe automatic retry.

Queue rejection, worker exceptions/Errors, external Future cancellation, failed UI handoff, validation/write failure and atomic replacement failure preserve active metadata and expose explicit Apply retry. There is no unchanged-frame retry loop. The existing synchronous preference write contract is unchanged. PreferenceFiles adds an internal prepared-file protocol; unsupported atomic replacement still fails without a fallback that could damage the previous destination. No backup/autosave/history feature is added.

Application metadata remains separate from project and User Config. Preparation, cancellation and activation do not touch committed project values, dirty/history state, private Properties or provisional seed text, or user preferences. Defaults affect future user-created resources only. Existing resources, copied/imported values and headless evaluation retain authored semantics. Public engine APIs, registry IDs/ranges, schema shapes and project/config/archive versions are unchanged. No new serialized fields are introduced.

Owner capture/projection/comparison, per-control checks, final rename/unlink and UI reset still have costs. Large-project/profile performance, provider durability/locking, physical inputs/DPI/OS focus and Windows 11 behavior remain unmeasured.
