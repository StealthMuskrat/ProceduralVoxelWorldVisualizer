# Runtime DPI composition and font density

Status: implemented on `codex/development-phase`, **uncompiled and untested**. Compilation, JUnit/native execution, independent replay and GitHub testing remain paused by owner instruction. No historical pass total or acceptance gate advances.

## Runtime composition

The desktop now samples main-window GLFW content scale and the backend's vertical framebuffer density before native NewFrame. User global scale remains a persisted 0.5–2.5 multiplier; per-window overrides retain their existing independent 0.5–2.5 range and inheritance intent. DPI is transient and never materialized into User Config or a project.

The frame's IO font scale is `user global × main content scale / framebuffer density`. A top-level window multiplies its user override by `target content scale / main content scale`. Combined logical font size is therefore `13 × user global × window multiplier × target content scale / framebuffer density`. Multiplication by framebuffer density during rendering gives the intended physical font size without applying the same Retina-style density factor twice. A 200% content scale with a 1:1 framebuffer doubles logical font height; a 200% content scale with a 2:1 framebuffer retains logical height while rendering twice as many physical pixels.

Main content scale comes directly from the actual main GLFW window, including relative/single-viewport mode, where `(0,0)` client coordinates cannot identify its physical monitor. Detached windows use their native viewport's DPI scale. The scalar follows the backend's horizontal content-scale convention and uses vertical framebuffer density to normalize font height; unusual anisotropic display setups remain unverified. Missing/nonfinite/nonpositive samples retain the last valid main/framebuffer component; unavailable detached DPI uses the main scale. Valid runtime factors clamp to 0.5–8. These bounds constrain transient backend input, not user preference ranges.

`DpiGlfwBackend` retains the pinned backend's input/platform behavior and refreshes its monitor work/DPI inventory each frame, so an OS DPI change need not wait for a monitor connection callback. Invalid backend monitor DPI values are normalized before native NewFrame. The backend retains only its owned main GLFW window handle and Java sample arrays; monitor/viewport wrappers are used locally and never retained. Invalid monitor DPI falls back to the latest valid actual-main content scale. See the [pinned GLFW backend](https://github.com/SpaiR/imgui-java/blob/v1.89.0/imgui-lwjgl3/src/main/java/imgui/glfw/ImGuiImplGlfw.java).

The desktop preserves the framework clear/GL/GLFW/NewFrame ordering, inserting sampling/composition after backend refresh and before NewFrame. This also removes the former global-scale assignment from process, which occurred after native font-base calculation. Frame DPI is thread-local and cleared by the outer frame's finally block, including rendering failures; existing startup/reentrant frame gating remains in control. A physical placement/monitor change during process is reflected by the following frame's sampling.

The pinned native source marks DpiEnableScaleFonts and DpiEnableScaleViewports experimental and advises against them. Both stay disabled. This implementation does not request the native bitmap workaround or automatic viewport/window-size rescaling. See the [pinned native flags](https://github.com/ocornut/imgui/blob/1d8e48c161370c37628c4f37f3f87cb19fbcb723/imgui.h).

## Font atlas and nested scopes

`UiFontAtlas` installs the existing embedded default font once before renderer initialization. It rasterizes at 52 pixels and sets the font scale to one quarter, retaining a logical base height of 13. The atlas uses one-times oversampling/pixel snapping, a desired width of 1,024, and an explicit 4,096-axis/16 MiB RGBA output budget. Build failure or an oversized output aborts initialization rather than publishing a partially valid atlas. The temporary ImFontConfig is destroyed after building; native atlas-owned decompressed font data and the resulting font remain owned by the context. The usual pinned GL backend uploads the atlas once and shares that texture across platform contexts; no DPI transition rebuilds an atlas or creates an additional font texture.

This is higher raster density, not proof of visual sharpness or a new typeface/license. Glyph advance/raster details can differ from the old 13-pixel bake even though logical font height remains 13. Magnification above the bake's density can still blur. GPU texture upload/sharing, screenshots, hardware texture limits and representative visual quality remain unverified.

The native font calculation multiplies only the current window and immediate parent's font-window scales. Child windows deeper than one level could therefore lose an ancestor's multiplier. Shared UiScale Begin wrappers now capture the effective parent font, then normalize the new native scope to that font adjusted for any target/parent DPI change. Production child windows, combos, menus, context/ordinary popups and modals use those wrappers. End calls and visibility/Apply/Cancel semantics remain unchanged. Native font state resets to a known local baseline before each adjustment, avoiding repeated multiplication across frames or nesting. The covered popup-bound helpers use this path when an offscreen owner recovers into a main viewport with different DPI.

Tooltips retain the pinned native SetTooltip replacement semantics. The binding's BeginTooltip operation does not expose the same replacement policy, so it is not used as a transparent replacement. Effective inheritance in deeply nested tooltip contexts, drag/drop tooltip appearance, full style/padding/radius scaling, title/tab sizing during a DPI transition, window-size migration and every production control's maximum-scale reflow remain separate work. This batch does not certify full specification 4.3/A32 or physical mixed-DPI behavior.

The scale-target registry advances to version 2 with the separate runtime DPI description/bounds and raster density; user scale composition, target names and preference shapes are unchanged. The existing reflective ContractGenerator reads this metadata, and its committed registry counterpart is updated without executing the generator. User/project schemas need no new fields. Appearance explains that display scaling is applied automatically.

## Deferred definitions

Fifteen `UiDpiPolicyTest` definitions cover old global/window composition, pixel-coordinate DPI, Retina normalization, detached/main ratios, framebuffer-invariant physical height, invalid/partial sample retention, finite clamping, unavailable detached DPI, rejected preference/cache ownership, normalized-frame validation, popup DPI transfer, invalid/overflow font metrics, project/preference/history separation and runtime registry metadata. They require no JNI/GL context.

`UiDpiProbe` defines a production dense-font bake and real UiScale root/three-deep-child/combo/popup scopes in an isolated ImGui context. Five explicitly synthetic DPI-frame cases cover standard density, content DPI 2 and 3, Retina density 2, and user global 2.5 times window 2.5 at content DPI 2. Actual mouse events open the combo; popup and nested native font sizes must match independent arithmetic. The atlas dimensions, raster/logical size and byte budget are recorded. Runtime scopes must retain each case's declared preferences plus private Properties/raw seed, project/history and dirty state. Python replay independently recomputes the frame/window/font equations and atlas budget.

Future Linux/Windows steps/artifacts are wired with unchanged development trigger exclusions. None has run. The probe uses synthetic frame values and no GLFW window/GL renderer: physical detached, physical DPI and GPU texture verification are explicitly false. Actual backend monitor refresh, OS DPI awareness, minimize/restore, mixed-DPI motion, font appearance, title metrics and full Windows 11 GUI acceptance remain pending. Existing native renderer/UI definitions remain queued for the later full validation pass.
