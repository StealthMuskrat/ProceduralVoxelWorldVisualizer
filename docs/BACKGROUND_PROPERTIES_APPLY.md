## Prepare an owned transaction outside the UI action

Desktop's explicit Properties footer Apply now captures the selected private resource and committed document owner, then prepares the candidate on the existing bounded editor executor. The worker replaces that resource in a private project copy, runs the captured complete validation policy, freezes its accepted values and constructs the structural Undo delta. It never reads the live EditorState or native controls. Current committed values and accepted visual previews remain active until successful UI publication.

DocumentSession adds requestEdit(Consumer<ProjectData>), EditRequest.prepare(), PreparedEdit.success()/diagnostics(), currentEdit(PreparedEdit) and applyEdit(PreparedEdit). Capture and publication belong to the document owner thread. Preparation may run on a worker; change/validation callbacks receive a private candidate and must not read or mutate the live document or concurrently mutate their retained inputs. The candidate is copied after validation and no mutable candidate accessor escapes, so later mutation of an input retained by a callback cannot change the completed preparation or its Undo delta.

Prepared diagnostics are immutable. A rejected result can still be current, allowing its diagnostics to be presented under the same captured policy. currentEdit checks this without rerunning validation or consuming the result; it returns false for another document, consumed result or changed source authority. Both successful and rejected editor completions pass this check before publication. applyEdit repeats ownership checks and consumes only an accepted result. The existing synchronous edit path uses the same history publication helper and retains its validation order.

The model guard includes the document lifetime, active object and exact JSON values, validation function identity, saved path/checkpoint/receipt, Undo/Redo heads and history-byte count. An identical second Save receipt still supersedes a pending edit. A no-op accepted result is consumed without replacing the active object, clearing Redo or adding history. A real change uses the existing bounded structural history, clears Redo and publishes one delta. This is an owner-thread optimistic protocol, not a general concurrent DocumentSession API or automatic retry mechanism.

## Cancel or reject without losing private correction

PropertiesApplySession owns an opaque request identity, exact ProjectFileOwner and FutureTask. It also captures the current diagnostics identity/values and scope so older Apply results cannot overwrite a newer Validation result. Before preparation and again at completion, it checks the current child-editor/navigation blocker. Reentrant cancellation cannot publish the retired request. UI publication additionally checks project identity/revision/values, selected resource/siblings, private draft object/values, raw seed ledger and saved path/dirty baseline. The model repeats history/checkpoint/policy ownership even when ordinary UI revision did not change.

The footer keeps its three logical actions. While running, Apply displays Cancel Apply and remains usable; Revert is disabled. Escape also retires the pending Apply while keeping the parent draft. Body input may still be corrected; changed private values retire the captured attempt instead of committing the older input. Running Apply blocks the existing source/project navigation gates. On failure, the draft stays available and Apply explicitly retries. A rejected candidate publishes compiler diagnostics but preserves source, history and correction text. A successful result commits once, refreshes Properties and increments the editor revision using the existing change semantics; later private edits need another Apply. It does not save the project or change preferences.

Cancel, stale context and lifecycle closure invalidate the identity, cancel the task and remove queued work where supported. Non-cooperative compilation can finish later but cannot commit or reopen the closed session. Scheduling, worker and UI-handoff failures release Running and produce bounded feedback. If document publication succeeds and later selection refresh fails, the result remains committed and reports that refresh failure; it is not retried or rolled back as an unapplied edit.

The Apply action has centralized context Help explaining the same ownership/cancellation boundaries. Legacy public PropertyPanel constructors and EditorState.applyDraft retain synchronous direct behavior. Guarded navigation/browser draft composition and other private settings Apply paths are not migrated by this batch. Child curve/expression/membership Apply continues to stage only its own private parent input. Project format 2, schema/registry shapes, scalar/voxel evaluation and dependency boundaries are unchanged; the prepared document API is additive and remains headless.
