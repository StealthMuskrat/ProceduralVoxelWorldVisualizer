# Collection withdrawal without host failure-text side effects

Development implementation on main; **uncompiled and untested** under the owner's testing pause. No compiler, Gradle, JUnit, native probe, schema/Python checker, independent consumer, packaging, real update request or GitHub workflow ran. The observed baseline remains **922 tests / 120 suites**. Native/Windows 11 and final release acceptance remain pending; no A01–A36 gate advances.

## Observe withdrawal without propagating the caller's failure

collectRegionAsync installed an internal whenComplete callback on its public request future to cancel undeliverable work. That callback needed only to observe terminal ownership, but whenComplete also propagates the source failure to its dependent stage. For a caller-supplied raw Throwable, the JDK may construct a CompletionException whose cause-derived message invokes host toString/getMessage. Those arbitrary text methods could therefore run merely because the engine installed its withdrawal callback, even though the engine never needed a description of the caller's outcome.

The internal observer now uses handle and returns a normal null value. It retains the existing task-cancellation action without forwarding the caller's exception into a failed dependent stage. Caller-supplied RuntimeException, Error, CancellationException and CompletionException outcomes keep their original identity and ordinary public-future cancellation semantics. The engine observer does not read their text or mutate their suppressed lists. This concerns the engine's own observer; public future get/join, asynchronous suppliers and arbitrary host continuations retain their separate JDK exception behavior.

The existing pre-admission/registration checks and 50 ms coordinator withdrawal poll remain. A blocked public completion callback cannot keep an undeliverable collection reservation. A generated RegionResult that loses publication is closed; a successfully published result still owns its reservation until explicit/idempotent close. Healthy shared subscribers retain their queued generation, independent contexts remain independent, and completed snapshots remain valid after closure. The engine neither adopts nor closes caller-supplied future values as generated results.

No completion executor, retry, public signature, saved format, schema/registry, deterministic field/voxel arithmetic or UI/preference behavior changes. Host code remains cooperative; no callback isolation, preemption, real-time bound or unusable-VM recovery is certified. Engine/model/storage retain their editor/native independence.

## Reconcile deferred delivery-Error expectations

Two older regression definitions still treated a consumer AssertionError as an exceptional coordinator result. The implemented delivery Error policy already normalizes such faults into the same per-chunk CONTINUE/FAIL_FAST path as failed acknowledgements. These definitions now match that contract rather than asserting the superseded terminal behavior.

RegionCompletionTest retains its four saturated-region reentrant successor cases: success, explicit cancellation, failed acknowledgement and directly thrown consumer Error. It now requires exact completed/failed/cancelled partitions for every case, including normal COMPLETED_WITH_ERRORS for a one-chunk consumer Error under CONTINUE. RegionProgressTest checks both orders and policies over its independently known 1,028 chunks: CONTINUE records 1,028 failed/zero cancelled and retains 1,024 details; FAIL_FAST records one failed/1,027 cancelled and one detail. Summary/progress snapshots must match, DELIVERY ownership/text remains exact, the original Error is unmodified, and successor generation remains usable. Genuine coordinator failures retain their separate exceptional terminal path. Both adaptations remain uncompiled/untested.

## New deferred coverage and independent replay

Two CollectionFailureObservationTest definitions use actual held workers. One matrix combines both orders, raw RuntimeException/Error/CancellationException/CompletionException outcomes and completeExceptionally/obtrudeException. It requires zero host text calls, original outcome identity, no suppressed mutation and reservation/request/queue release while the worker remains held. Another holds a later host callback while withdrawal releases the lease, keeps a healthy shared peer queued and eventually completes its immutable EMPTY snapshot. Normal handle values keep the harness from formatting the host failure itself.

CollectionFailureConsumer is invoked by the existing engine-JAR-only RegionCompletionConsumer. Roots 2/4, both orders, four fault forms and two terminal operations define **32 cases with zero host text reads**. Public parent gates hold an independent context's generation worker while collection work shares a queued chunk with a healthy peer. Withdrawal must release collection bytes before the gate opens, keep the peer and its one queued flight, retain the original caller outcome through late engine publication, and leave the independent holder usable.

The added replay retains **32 peer chunks with 1,152 exact EMPTY-cell expectations**, checked after all contexts/engines close. The original RegionCompletionConsumer 1,024 world-cell/72 retained-cell replay, existing progress replay, authoring JSON comparison, native receipts and other independent dimensions remain unchanged. The future report is region-completion output/collection-failures/collection-failure-report.json, beside the existing independent reports. No report was generated. Existing manual-only Linux/Windows commands already compile all example sources and invoke RegionCompletionConsumer; no workflow command or trigger changes are needed.

Source review and git whitespace/content/metadata checks are the available verification. Remaining feature/failure audit, runtime/concurrency/stress validation, native/Windows 11 and release acceptance remain outstanding.
