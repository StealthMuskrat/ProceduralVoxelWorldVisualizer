The Performance category now offers Performance limits and Update trust as separate retained sections. `PerformanceSettingsPage` draws only the selected form, so one private form cannot consume the other's action space. Changing sections retains both panel/session instances and their exact buffers; it performs no Apply, Revert, network check or file write. The update-check configuration action selects Update trust directly, and Visualization's Edit preview limits action selects Performance limits. The current section is transient UI navigation, with no new persisted key.

Performance limits uses one scrolling body with wrapped labels above full-width exact integer fields. Apply Performance, Revert Performance and Show Invalid Limit occupy a persistent measured row. Correction navigation first resolves a displayed/owned mismatch, then field feedback in registry order, including the coupled default-extent error. It requests focus/scroll without parsing, normalizing or replacing text. The existing complete displayed-map/current-base checks, 128-character provisional bound, exact signed long parsing, coupled extent validation, restart notices and atomic publication remain in their original owners.

Show Update Fields alternates endpoint/origins focus and scroll requests; it does not change either string. Existing provisional/historical limits, complete displayed checks, HTTPS/origin validation, canonicalization, active-base ownership and atomic publication remain unchanged. Editing/navigation makes no network request.

Workspace uses a scrolling body with bounded checkbox hit targets and wrapped labels. Restore Default Docking and, when supplied by the host, Center Main Window remain outside that body. Their existing callbacks retain responsibility for docking/GLFW work; the panel does not implement or certify physical centering. Multi-viewport and tool flags keep their existing immediate User Config behavior, including the restart boundary for native viewport configuration. They do not enter project history.

Each production form has its own ordinary Save Preferences button inside the body, using the same existing desktop save handler. The desktop does not append a second save button below these footers. Ordinary saves write active preferences and retain private performance/trust drafts. Failed Apply retains retry state, and one form's accepted Apply merges unrelated active preferences without applying the other form. Schema/registry/range/version definitions, headless API, engine ownership and project/private Properties semantics are unchanged. No resize or section change starts generation, profiling or an update check.
