# Diagnostic footer decisions

Status: **uncompiled and untested** on `codex/development-phase` under the owner testing pause. This follows [diagnostic workspace layout](DIAGNOSTICS_LAYOUT.md) and [diagnostics and recovery](DIAGNOSTICS_AND_RECOVERY.md). The validated baseline remains 922 tests / 120 suites.

Logs, Notifications and Validation Results collect the complete persistent footer before accepting at most one action in displayed order. Escape suppresses that frame's footer. Stable body, field, child and row identities remain outside the new footer scopes. Each panel instance has a transient UUID; action IDs also include a presentation version. Closing, hiding or collapsing a tool releases its footer scopes while retaining filters, selections and immutable history/results. Returning to a tool requires a new gesture.

Logs and selected-notification footers belong to the current document lifetime, exact retained immutable Entry and navigation availability. A changed selection, repeat, acknowledgement, eviction or changed destination eligibility retires the former gesture. Equal stable event IDs alone do not authorize an action. Unrelated history publications retain the selected Entry reference and therefore retain its Copy/navigation presentation. The existing store remains authoritative: displayed-entry read/resolve/dismiss operations reject changed occurrences under synchronization, and navigation marks the reviewed occurrence read before invoking the source callback. Reading does not resolve an action; resolution does not dismiss its history.

Mark All Read has a separate exact immutable View scope, independent of the selected-entry scope. A new view between press and release cannot be adopted by the held predecessor. Publications during an accepted draw still use the store's reviewed-view operation: only unchanged entries in that reviewed view become read, while newer or replaced occurrences remain unread. This preserves bounded store semantics without introducing a UI callback or lock per publication.

Validation footers belong to the exact result publication and selected row, including two indices containing the same Diagnostic object. The selection owner now exposes opaque publication/selection tokens. Reselecting one index keeps its token; changing indices or refreshing a publication replaces it. Existing document/project/revision/scope/list ownership and in-place value/order checks remain authoritative. Validate, Copy and source navigation cannot transfer a held gesture to a replacement result, a different selection or a same-UUID reopened document. Validate still examines only the committed project and replaces the read-only result publication.

Clipboard, source-navigation and Open Logs callback RuntimeExceptions are contained after footer collection. The editor records a required APPLICATION error under DIAGNOSTIC_COPY_FAILED, DIAGNOSTIC_NAVIGATION_FAILED or DIAGNOSTIC_LOGS_FAILED. Messages are bounded to 1,024 UTF-16 units and a missing/blank message uses the exception class name. These failures do not escape the native draw scope or attach feedback to an unrelated successor entry. Ordinary Copy and failed callbacks do not resolve an action. A source callback failure keeps the existing pre-callback read acknowledgement; it does not roll it back. Unrelated failure publications retain the selected-entry retry IDs.
