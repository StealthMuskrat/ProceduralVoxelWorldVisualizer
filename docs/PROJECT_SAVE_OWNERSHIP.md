# Project Save ownership — unvalidated development

This main-branch batch supports specification 2.6.3–2.6.4, 3.5, 19.2.6 and 19.6.2, with A05/A07/A22 definitions. Compilation, JUnit, native probes, independent consumers, checkers, packaging and GitHub workflows remain paused. The last observed validated baseline remains 922 tests / 120 suites; the following implementation and definitions are not executed acceptance evidence.

## Validate an owned snapshot in both Save paths

Synchronous DocumentSession.save previously passed the active project directly to its custom validator; prepared/background Save passed an owned candidate. A rejecting or throwing custom validator could consequently change committed synchronous data without a transaction, while a success-reporting validator could change what was written. Both DocumentSession paths now use requestSave/prepare/applySave, retaining the existing public signatures and explicit atomic publication boundary.

SaveRequest captures committed JSON values and an owned snapshot. Each preparation makes its own validation candidate and captures that candidate's JSON immediately before invoking the custom validator. Diagnostic rejection becomes IOException and validator exceptions/errors retain their original identity. A success-reporting validator whose candidate values changed is rejected with a read-only validation error before filesystem admission. Retaining or later changing that private candidate cannot alias the active document or the captured request. Validation still precedes the existing structural check, serialization, sibling write and force. Ordinary custom validation occurs once per preparation.

This isolates candidate mutations; it does not roll back an explicit side effect against a captured DocumentSession, another file or other external state. Managed or raw live changes during validation are rejected by the existing prepublication checks, and the newer state remains. The default validation/compiler policies are read-only. Custom worker validators must continue to support candidate-only calls, and callers must hand preparations back to the owner thread before Apply.

## Checkpoint receipts distinguish equal-value Save completions

DocumentSession now maintains an opaque, private checkpoint receipt. New/Open and each installed successful Save checkpoint replace it. A same-path, same-value Save therefore has a distinct completion even when the active reference, lifetime, saved text and dirty status are identical. Save/Open requests and edit/Undo/Redo transaction owners capture the receipt; a newer completion rejects an older pending operation before it can replace a file, install a document or move history. Failed saves install no receipt. Receipts are not serialized, retained in history or exposed as a public format/version/API change.

Apply checks current owner, validator, active reference, lifetime, path, saved text, receipt and committed values before atomic replacement. A receipt for the next checkpoint is allocated before replacement. After successful replacement, it installs the exact written text/path only while the captured lifetime and prior receipt still own the checkpoint. A reentrant New, same-UUID Open or newer Save completion at the injected publication boundary retains its own metadata. The older file publication remains a success; it cannot be undone or honestly reported as an unpublished failure.

Later edits within the same document lifetime do not themselves install a checkpoint receipt. If only such raw or managed edits occur at publication, the completed file remains the exact saved baseline, and those newer values remain dirty with their history intact. This differs deliberately from allowing an older Save As to overwrite the path/checkpoint of a newer completed Save. Existing desktop save-before-New/Open/Exit checks still require current decision authority and a clean matching saved document before continuing.

Synchronous cleanup retains the original IOException, RuntimeException or Error across unpublished close failures, suppresses a distinct cleanup failure and avoids self-suppression if the same throwable is reused. Successful publication makes close perform no filesystem operation. Explicit prepared callers retain their existing close/retry responsibility; a failed cleanup can leave an unpublished sibling. Atomic replacement requirements and the absence of an ordinary-move fallback remain unchanged.
