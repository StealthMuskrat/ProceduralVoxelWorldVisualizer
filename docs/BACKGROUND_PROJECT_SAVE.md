# Background Project Save — unvalidated development

This source batch supports specification 2.6.3–2.6.4, 4.4, 18.7.2–18.7.3 and 19.2.6 and A03/A05/A32. Compilation, JUnit, native probes, independent consumers, Python checkers, packaging and workflows remain paused. The last observed validated baseline is still 922 tests / 120 suites. Source implementation and deferred definitions do not establish passing acceptance evidence.

## Prepare without replacing the destination

Desktop Save and Save As now capture an owned committed snapshot, then validate, serialize, write a temporary sibling and force its contents on the existing bounded background executor. Neither preparation nor queued UI completion can mark the document saved or replace the destination. The Saving modal keeps drawing and offers Cancel Save; Escape cancels the same request. Properties/raw seed input, selected resources, project identity/lifetime, revision and Undo history remain outside the saved snapshot's publication.

The UI consumes the owned preparation only when the original request still owns the project, private inputs, path/checkpoint, selection and validation policy. A complete committed-value comparison catches direct edits that retain the same object/revision/dirty state. Publication performs the final atomic rename and installs the exact text actually written as the saved checkpoint. Unsupported atomic replacement rejects without an unsafe fallback. Successful publication transfers the temporary path and has no subsequent filesystem cleanup that could relabel the save as failed.

Cancel or stale ownership retires the mailbox version and the queued Future. Completed unpublished siblings are closed; workers finishing after cancellation dispose their own late result instead of publishing it. Rejected scheduling, compiler/write/force failure, terminal UI-handoff failure and failed replacement return to an explicit Save path decision with a bounded error and the entered path retained. Temporary cleanup errors are posted separately through the thread-safe event service; they cannot overwrite a later request or the original failure. A failed cleanup may leave an unpublished temporary sibling; model callers retain close ownership for an explicit cleanup retry. No automatic repair/backup/recovery-file workflow is introduced.

A save required before New, Open or Exit continues only after successful publication and a final owner check. Failure or cancellation discards that pending transition. Retrying the failed Save is standalone and cannot resume the old destructive action. A saved snapshot followed by a reentrant change at publication remains a real saved file with the newer document still dirty; the transition is aborted rather than discarding those edits. Completion errors are reported after the successful save point, and predecessor cleanup cannot clear a successor request. Desktop lifecycle closure retires both Open and Save preparation.

Ownership snapshots and the final rename/temporary deletion still occur on the UI thread. Preparation moves the expensive validation, serialization, file write and force out of the UI action; it does not guarantee a latency bound for a filesystem rename, unlink or very large ownership comparison. Draft Apply and other project/resource IO remain in the broader responsiveness audit. Save remains explicit, with no autosave, project backup, recent-project history or startup reopening. Project/schema versions and generated semantics are unchanged.

## Additive headless model API

DocumentSession.requestSave(path) captures its active identity/lifetime/path/checkpoint, current validator and owned committed values on the document thread. SaveRequest.prepare() may run on a worker; it validates a private candidate and returns PreparedSave after the unpublished sibling has been completely written and forced. PreparedSave has no mutable project accessor and implements AutoCloseable.

On the owning document thread, applySave(prepared) rejects a foreign owner, changed policy, managed or raw committed changes, a closed preparation or a consumed preparation before replacement. It performs one atomic replacement and sets path/checkpoint without replacing the active model, lifetime or history. Close every unpublished preparation, including cancelled/stale candidates; successful publication makes close a no-IO operation. Failed close retains staging ownership for explicit retry. Custom validators must support candidate-only worker calls; DocumentSession remains otherwise owner-thread confined. A real executor/Future/UI queue supplies the handoff visibility.

The existing synchronous DocumentSession.save and ProjectIO.save paths retain their signatures and original contracts; isolated legacy decision fixtures still use the immediate workflow constructors. Desktop's existing background dialog factory now selects background preparation for both Open and Save. Prepared-save model types introduce no editor/native dependency.
