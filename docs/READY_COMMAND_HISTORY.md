## Delivered work remains cancellable

Background ResourceEditSession and ProjectHistorySession previously published their prepared results in queued UI callbacks. Both now retain prepared values or worker failures in one-slot CPU mailboxes. Delivery marks readiness without changing the pending/preparing state, work version, shown Cancel authority, document, history stacks, private Properties input, selection or completion callbacks. Queued UI callbacks capture request identifiers rather than prepared candidates and command destinations. Retiring work clears its CPU payload independently of draining those callbacks; a retired worker cannot refill the slot.

ResourcePanel uses the shared navigation dialog's current decision ticket and shown work version. It processes Apply/Discard/Cancel/Escape, unwinds the native popup and only then accepts that exact prepared command. Clean requests still start immediately and expose their progress/Cancel controls. Combined Apply validates private Properties independently before the command, while Discard runs the command against committed values and disposes of private input only after publication. Exact source/private/raw/selection/diagnostic/checkpoint/history/policy checks and the short reconciliation/completion fence remain in place. Successful publication consumes one undoable edit; an accepted no-op retains Redo. Clipboard/UI completion still runs only for an accepted command.

ProjectHistoryPanel likewise handles current Cancel/Escape and its discard decision before acceptance after popup unwind. A separate work version fences preparation started by a same-frame Discard, while request/dialog identity guards successor requests. Clean Undo/Redo preparation retains the same cancellation path. Ready publication repeats source/private/raw/checkpoint/history/policy checks, consumes the request and installs the prepared step under the existing movement/refresh fence. History never applies private Properties; explicit discard takes effect only when movement succeeds. History bytes and the one-step Undo/Redo behavior remain unchanged.

Both paths still complete from the original authorized action without another confirmation or Apply click. Ready worker failures/rejections can be cancelled before feedback is installed. Accepted failures retain existing explicit clean Retry Action, dirty Apply/Discard or fresh Undo/Redo recovery. Scheduler, external-Future and UI-handoff failures keep their existing recovery; unchanged frames do not resubmit. Cancellation, clear, reset, document replacement and close retire ready work, with private input retained on cancellation. Synchronous direct constructors preserve their prior behavior.

Acceptance also captures its original request before refresh. A stale-command completion callback may create a successor, including one prepared synchronously; the old acceptance cannot consume that successor. Publication blocker callbacks may similarly cancel and create ready successors, which require their own acceptance. Late/duplicate delivery cannot consume another request or repeat a committed edit/history movement after refresh failure.

No public model/engine signature, serialized format, schema, registry, scalar/voxel rule, project Save or user-preference behavior changes. Snapshot capture, full comparisons, diagnostics, final installation and selection/UI refresh retain owner-thread cost. Running compilation cancellation is best effort, and a running worker can retain its own inputs until exit. No measured latency/memory, physical input, OS/DPI or complete Windows 11 claim is made. Other background completion paths remain separate work.
