The observed baseline remains **922 tests / 120 suites**. ## Ordinary Save and periodic workspace capture

Desktop Save Preferences and the existing visible-window five-second periodic save now use one PreferenceSaveSession on the bounded editor executor. A manual save first captures current tool visibility and docking data. Native capture stays on the owner thread. The session captures a detached complete active UserConfig, and the shared PreferenceApplySession/PreferenceFiles protocol validates a private snapshot, canonicalizes its detached binding map, encodes and forces an unpublished sibling on a worker.

UI delivery does not publish. At the end of normal control processing, the owner rechecks complete active values before required atomic replacement. This request writes no live fields: nested preference owners, maps and raw active values retain identity. Ordinary persistence cannot activate a private theme/binding/scale/performance/trust draft, change project/history/dirty state, replace the engine or consume private Properties/raw seed text. Private Apply continues to own its own activation.

Repeated manual/periodic requests share one logical save; a manual request promotes completion feedback to one concise success status. Ongoing slider/window changes do not cancel a still-writing or queued worker every frame. Once a prepared result is available, changed active source values retire its unpublished file and capture one latest successor. Older/duplicate deliveries cannot publish into that successor. No stale full snapshot is installed over newer active preferences. A private Apply that wins first is included in the successor; an ordinary Save changes no live values and therefore does not invalidate an otherwise current prepared private Apply.

Continuous edits can postpone persistence until a prepared snapshot is still current. There is no claimed deadline or hard bound on total preparation attempts during ongoing changes. Queue admission, work, handoff and file bounds remain the shared executor/protocol limits. Final rename and unpublished-file cleanup still occur on the owner thread, and owner snapshot/full-source comparisons retain their cost.

## Failure and lifetime behavior

Queue rejection, external Future cancellation, handoff failure, complete-config validation, write and unsupported/failed atomic replacement retain active values and the previous destination. A failed attempt does not retry on unchanged frames or unchanged periodic ticks. Explicit Save Preferences permits retry; changed active values permit a new attempt on the next ordinary periodic tick. A snapshot-capture/comparison failure suppresses periodic retry until explicit Save, because no reliable failed-source value exists. Bounded error feedback uses PREFERENCE_SAVE_FAILED. Reporting and post-save status failures cannot strand the session or repeat an accepted save; success consumption precedes callbacks, including reentrant successor requests.

An ordinary active save belongs to the Desktop, independently of any settings panel. Hiding/changing Settings preserves it. Final lifecycle closure invalidates unpublished handoffs; late workers may finish their own temporary-file cleanup but have no publication authority. Interrupt/removal is best effort for in-flight filesystem work. Failed cleanup can leave an unpublished temporary file with error feedback; it cannot retry a consumed pathname or overwrite the destination.

Normal visible application exit captures the final normal-window geometry, visibility and docking state, retires every older ordinary-save request and performs one synchronous final save before native teardown. This deliberate exit barrier retains the existing final-persistence guarantee without depending on a UI delivery after the loop stops. Final-save failure preserves the old destination and propagates through the existing lifecycle failure path; earlier workers cannot later overwrite it. Failure/startup cleanup before successful visible exit does not implicitly flush preferences. Public UserConfig.save, independent EditorState.close behavior and direct synchronous APIs remain compatible. No serialized format/schema, headless dependency or workflow trigger changes are introduced.
