## Recover representable interpolation after intermediate overflow

BLEND and expression lerp evaluated a + (b-a)*weight directly. Finite opposite-sign endpoints could overflow their difference before a representable weighted result was formed. RAW extrapolation could similarly overflow the weighted difference even when cancellation with a yielded a finite result. For example, equal blending between -Double.MAX_VALUE and Double.MAX_VALUE has a zero result, and lerp(2^1023, 0, 2) has a finite -2^1023 result; the ordinary intermediate calculation previously failed.

A shared package-private FiniteInterpolation helper first evaluates the original expression with the same double operation order. Every finite result returns immediately, preserving its raw bits, signed zero, subnormal behavior and normal rounding. There is no reassociation, fused operation, implicit normalization or precision change on that path.

Only when that result is nonfinite and all three operands are finite does the helper evaluate the same affine expression using exact BigDecimal representations of the actual binary doubles. It uses the double constructor rather than rounded decimal display text, applies no intermediate MathContext rounding and converts to double once at the end. Finite-double operand sizes bound this fallback's arithmetic; a truly out-of-range final value remains nonfinite and reaches the existing executing boundary. Nonfinite inputs retain the ordinary result/error policy without entering decimal conversion.

ScalarRemapping.Plan combines finite mode targets through this helper, so editor transfer previews and compiled BLEND use the same result. Expression lerp uses the same helper through the existing function table, including named/indexed evaluation and constant folding. Blend zero/one endpoint short-circuiting remains in the existing compiler/plan; expression function arguments retain their existing eager evaluation. RAW extrapolation, explicit weight Clamp and output Clamp_01 remain unchanged. Nonfinite ADD/SUBTRACT/MULTIPLY/DIVIDE targets still reject before interpolation, and truly nonrepresentable final values still reject before output clamping. This does not widen the arithmetic policy of other expression operators, inverseLerp, Remap Range, World numeric drivers or curve evaluation.

The canonical BLEND description and tracked processing registry state this policy. Public method signatures, operation/function IDs, input/control signatures, registry/project/archive versions and schema shapes remain unchanged. Previously rejected representable extreme interpolation can now produce corrected scalar/voxel values; existing finite ordinary results and previously written exact archives are not rewritten. This is a numerical correction, not a claim that every finite computation is exactly rounded. The fallback may allocate and cost more than ordinary double arithmetic; no throughput/latency benchmark or representative hardware measurement ran.
