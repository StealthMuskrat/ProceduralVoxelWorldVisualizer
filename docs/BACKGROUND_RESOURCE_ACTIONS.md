This main-branch source batch supports specification 2.6.5, 3.1–3.5, 4.1–4.4, 6.14.5, 18.6.1–18.6.3 and 19.6.2, with deferred A03/A06/A08/A09/A22/A32 expectations. ## Prepare complete browser transactions outside the UI action

Desktop ResourcePanel now uses the bounded editor executor for Create, Duplicate, Copy/Cut Paste, inline Rename, confirmed Delete/replacement, placement insertion, ordering, Move and completed drop transactions. An unchanged Properties draft starts preparation immediately. A modified draft or provisional seed still requires the existing Apply / Discard / Cancel decision. Committed document values, the current selection and exact private input remain active until queued owner-thread publication.

The worker owns captured source values, the frozen resource command and, for Apply, an isolated copy of the active Properties resource. It constructs the complete candidate, performs required intermediate/final validation, freezes accepted values and builds the structural Undo delta. Command factories already own UUID lists, names and inserted definitions; clipboard copies own captured definitions and cuts resolve identities in the captured candidate. Newly generated Duplicate/Paste identities belong only to their resulting candidate. Worker code never reads live EditorState or native controls. Selection metadata crosses the handoff as an immutable UUID selection, and is reconciled only after successful publication.

Legacy direct ResourcePanel/ResourceEditSession constructors retain synchronous behavior. The worker path adds no project format, schema, registry, scalar or voxel semantics changes. Existing model/engine dependency boundaries remain headless.

## Preserve independent draft validation before the action

DocumentSession adds the overload requestEdit(initialChange, intermediateValidation, finalChange). Capture stays on the owner thread; EditRequest.prepare may run on a worker. Preparation copies captured source values, runs initialChange, copies the intermediate diagnostic list, and stops on rejection. Only an accepted intermediate candidate reaches finalChange and the document's captured final validation policy. Accepted values and history are frozen using the existing prepared-edit path. No mutable candidate accessor escapes.

EditorState.requestBrowserEdit uses that overload for combined Apply: first replace the captured active private resource, then independently compile/validate that project with NoiseCompiler, then run the browser command, then validate the final candidate under the captured document policy. An invalid private resource cannot be hidden by a Delete or replacement command that would remove it. Invalid provisional seed text rejects before scheduling any Apply. Discard runs only the resource action against committed input; it disposes of private input only after successful publication.

Intermediate rejection returns immutable PreparedEdit diagnostics with the same document/checkpoint/history/policy authority as final rejection. currentEdit must pass before either diagnostics or accepted data publish. Successful publication consumes the preparation once. A real change is one existing bounded structural history entry; an accepted no-op retains active identity, Redo and history bytes. Selection stays outside Undo/Redo.

All callbacks receive private candidate state and must not access the live document or mutate their retained inputs concurrently. The captured document policy remains the final authority even when an intermediate checker is supplied. This is an additive optimistic owner-thread API, not general DocumentSession cross-thread safety. The single-change overload keeps its existing validation order.

## Guard cancellation, retries and completion

The UI actor owns the exact opening project lifetime/object/revision/values, selected UUID/siblings, private draft object/values, raw seed ledger and saved path/dirty baseline. Prepared-document guards additionally cover validation-policy identity, saved checkpoint/receipt and Undo/Redo heads/bytes. Even an identical second successful Save supersedes already prepared work. Shared diagnostic identity/values/scope protect newer validation. Private-editor eligibility is checked at admission and completion, with ownership repeated after the callback. Duplicate decisions, reentrant admission and retargeting cannot schedule another task.

The shared modal retains three logical action slots. Preparing Apply... identifies combined Apply; Preparing action... identifies command-only work. While running, Apply/Discard are disabled and Cancel/Escape remains usable. For an initially unchanged draft, failed preparation exposes Retry Action and keeps Discard disabled, including when no resource was selected. A dirty-draft request retains the explicit Apply/Discard choices after failure. Changed correction text requires Cancel and a new owned command request. There is no automatic retry.

Preparing is separate from the short existing publication/reconciliation fence, so Cancel, reset and lifetime replacement can retire work. Clear/reset/close invalidate the opaque identity, cancel/remove queued work where supported, and suppress late completion. Desktop's ResourcePanel lifecycle now closes its edit actor and clears unpublished UI completion in addition to selection/export cleanup. Non-cooperative worker completion cannot apply or affect a successor or disposed pane.

Rejected candidates preserve exact private values, seed text and current document/history. Scheduling, action, validator, admission or handoff failures release Preparing and report bounded RESOURCE_EDIT_PREPARE_FAILED feedback for explicit recovery. Successful publication retires the old command, advances editor revision, then reconciles selection and invokes its consumed UI completion under the publication fence. Reentrant requests/cleanup cannot replay the edit. Refresh failures, including Errors, report a completed action instead of rolling it back or treating it as an unapplied candidate. The existing cut-completion identity check preserves a newer clipboard. Saving and preferences remain explicit and independent.

Central Help adds Resource actions with private Properties and relates it to the resource-session guide. The synchronous browser transaction notes remain historical/direct-workflow documentation; this follow-up changes Desktop execution and clean-action failure recovery.
