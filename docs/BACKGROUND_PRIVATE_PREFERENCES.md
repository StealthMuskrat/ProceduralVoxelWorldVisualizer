# Background private preference Apply

Development implementation on main; **uncompiled and untested** under the owner's testing pause. No compiler, Gradle, JUnit, native probe, consumer, Python/schema checker or GitHub workflow ran. The observed baseline remains **922 tests / 120 suites**. This source coverage does not certify complete Trees 2.2/4.4/19, A22/A32/A33, Windows 11 hardware or final release acceptance.

## Shared preparation, separate private forms

Production Performance limits, UI Scales and Update Trust now share PreferenceApplySession on the existing bounded editor executor. Each form retains its own complete typed raw text, cached parsing feedback and active-value base. An explicit Apply captures an owned UserConfig source and immutable candidate values. A worker reconstructs a private preference snapshot, applies only the requested form's values, validates the complete configuration, serializes it and forces a private sibling file through the existing prepared PreferenceFiles protocol.

The delivered file remains unpublished until the panel processes its current input. A normal successful Apply completes from its original action; no second confirmation is added. Cancel Apply, Escape and Revert can win before the final atomic replacement, including a completion-ready frame. Form editing supersedes pending work. Hiding/collapsing Settings, changing its category/subsection or final panel shutdown retires the request; the retained private form survives suspension. Limits, scales and trust remain independent private buffers.

Apply/Cancel Apply native identity includes the request version. Revert keeps its private opening identity across worker delivery. The owner checks the exact session generation, active form values and complete displayed raw input, then the entire current UserConfig before publication. Numeric-equivalent text edits and explicit equal-value Revert still retire old authority. Newer preferences from another form, a live control, workspace update or another private Apply cannot be overwritten by an older full-file snapshot. If unrelated preferences change, review and explicitly retry against their latest values; a changed owned domain requires Revert first.

## Atomic publication and domains

Final replacement remains the existing required atomic rename on the owner thread. On success, activation installs only the owned preference fields without intervening validation, copying or callbacks. The performance patch includes all fourteen limits/default extent fields; the scale patch preserves unknown/extension window multipliers while updating global and known overrides; the trust patch installs its validated endpoint/allowlist. Nested active preference owners remain in place. A request is consumed even for an accepted equal-value publication.

Consumption precedes panel reload and native font/layout consequences. Subsequent refresh failures cannot repeat the accepted write. Successful cleanup never unlinks a reused temporary pathname. The owned mailbox releases unpublished siblings on cancellation, failed handoff, stale input or late worker completion. Cleanup/reporting failures cannot strand the next request; failed unlink is terminal for that pathname and can leave an unpublished temporary file with error feedback. Interrupt/queue removal is best effort, not a hard deadline for filesystem work.

Queue rejection, worker exceptions/Errors, external Future cancellation, UI handoff failure, complete-config validation/write failure and unsupported/failed atomic replacement preserve active values and the previous destination. The private correction remains available for explicit Apply retry or Revert. There is no unchanged-frame retry loop. Concurrent private forms are serialized by source ownership: after one changes active preferences, a second result must be reviewed and retried rather than losing that first change.

Ordinary Save Preferences continues to persist only active values and never implicitly applies a pending form. A later authorized explicit Apply may subsequently replace that file with its candidate if active values are still current. Theme and shortcut scheduling is extended by the later [background Theme and Binding follow-up](BACKGROUND_THEME_AND_BINDINGS.md); ordinary/workspace preparation scheduling is changed by the later [active-save follow-up](BACKGROUND_ACTIVE_PREFERENCE_SAVE.md). Update Trust configuration performs no update request or URL launch. Existing engine instances are not recreated; original restart notices remain authoritative.

Project values, explicit project Save, history/dirty state, private Properties and provisional seed text remain independent. Generation rules, persisted absence/inheritance, public headless APIs, registry IDs/ranges, schemas and configuration/project/archive versions are unchanged. Direct panel/session constructors and synchronous UserConfig.apply* APIs retain their behavior; production opts into background scheduling explicitly.

Owner snapshot capture/comparison, cached per-control feedback, final rename/unlink and widget reload still have costs. Full source checks can cancel preparation during unrelated preference changes. No measured large-config/provider/latency guarantee is claimed; physical input, DPI/OS behavior, locking/durability, memory pressure, native and Windows 11 acceptance remain pending.
