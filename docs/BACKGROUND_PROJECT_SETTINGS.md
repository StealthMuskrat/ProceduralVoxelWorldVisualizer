# Background Project Settings Apply — unvalidated development

This main-branch source batch supports specification 2.6.5, 4.1–4.4, 6.14.5, 18.6.1–18.6.3, 18.7.3 and 19.6.2, with deferred A03/A09/A22/A32 expectations. Compilation, JUnit, native probes, independent consumers, Python checkers, schema generation, packaging and GitHub workflows remain paused. The last observed validated baseline remains 922 tests / 120 suites. These source changes and future replay definitions do not advance acceptance status.

## Prepare the complete settings candidate on a worker

Desktop Project Settings now uses the existing bounded editor executor and prepared document-edit protocol. Apply first checks ownership of all three displayed raw strings, signed decimal parsing and inclusive minY <= maxY. It captures the exact opening project and a DocumentSession.requestEdit for the parsed seed/minY/maxY. Its worker copies the owned source, changes only these project settings, runs the captured full-project validation policy, freezes accepted candidate values and constructs the structural Undo delta. Worker code never reads live EditorState or ImGui controls. Current committed project values remain active until queued UI publication succeeds.

The original ProjectSettingsSession and public ProjectSettingsPanel constructors retain synchronous behavior for direct workflows. Desktop explicitly selects the background constructor. No public engine API, project format 2, schemas, registry shapes, scalar arithmetic or voxel placement semantics change in this batch; it reuses the prepared edit API introduced by background Properties Apply.

## Own the exact text and current document

The settings session owns its exact raw seed/minY/maxY spellings, project object, logical UUID, opening editor revision, original settings and complete opening project JSON values. Applying mismatched displayed text or invalid input cannot schedule an earlier parsed value. Editing a pending field retires its job even when the replacement spelling parses to the same number. An identical text notification and duplicate Apply do not schedule another task. A detected hidden raw source mutation permanently marks that settings session stale; explicitly Discard and Reload before applying again.

Publication additionally checks the prepared edit's document lifetime, exact source values/object, validation-policy identity, saved path/checkpoint/receipt, Undo/Redo heads and history byte count. An identical second Save receipt supersedes pending work. Rejected candidates pass the same currentEdit check before their diagnostics can replace shared results. The captured shared diagnostic list identity, values and scope prevent an older settings attempt from overwriting a newer Validation result. The current child-editor/navigation/file/import/export blocker is repeated at admission and completion, including after callbacks that can cancel or change context. Admission also fences recursive Apply.

Separate private Properties values, selection and provisional seed text are deliberately independent from Project Settings ownership. Settings publication does not refresh or discard that draft. A real accepted settings change publishes one structural history entry and increments the editor revision. An accepted raw no-op consumes its settings draft without replacing the active document, adding history or clearing Redo. Neither operation saves the project or preferences.

## Cancel, correct or explicitly retry

Apply becomes disabled Applying... while preparing. The three body fields remain editable; a change cancels the old preparation and keeps the newly typed text. Cancel and Escape close/discard this private settings draft, including pending work. Desktop page switching, window-X, coordinated file transitions and lifecycle closure retire its request. Collapsing the host retains the draft and may still receive a current background result. Work identities and task cancellation prevent late or non-cooperative completion from publishing or affecting a reopened successor.

A work-version fence retires old footer gesture ownership when work begins or ends, without changing input identities or stealing field focus. Cancel/Escape takes priority over a held Apply release. Queued tasks are removed from the executor where supported. Failure to schedule, prepare or hand off a result ends Applying, retains exact correction text and reports bounded PROJECT_SETTINGS_APPLY_FAILED feedback. Retry requires another explicit Apply; there is no automatic resubmission. Compiler rejection retains up to 256 immutable attempt diagnostics with the complete count, while the panel draws at most eight bounded details. A later fatal failure clears earlier candidate details. Current shared validation storage keeps its existing separate scope and bounds.

Central Project Settings Help describes worker preparation, text ownership, cancellation, separate Properties retention and explicit save/retry. The four existing footer actions remain Apply, Cancel, Discard and Reload, and Show Problem.
