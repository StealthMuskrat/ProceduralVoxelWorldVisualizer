# Portable resource file safety

Status: implemented on `codex/development-phase`, uncompiled and untested. GitHub testing remains paused by owner instruction. Earlier Import/Export evidence does not validate this extension.

The package file dialog previously initialized its path from the active project filename, then exported with a direct truncating write. Export now proposes a separate `.pvresources.json` sibling, such as `terrain.pvresources.json` beside `terrain.pvproj.json`. An unsaved project proposes `resources.pvresources.json`. Import uses the same package-specific suggestion instead of preselecting the project JSON. These are initial suggestions; the user still chooses a path explicitly.

`ResourcePackageFiles` rejects blank/invalid path input and refuses an export destination that names the active project file. Protection checks normalized locations, existing same-file identities (including hard links), and resolved symbolic links/parent locations, including dangling project links. It checks before directory creation, after parent preparation and again after temporary staging. A rejected path never replaces the project document. These checks protect the active project's current path; they do not infer every other project a user may have stored elsewhere.

Export owns a copy of the dependency payload and validates it through NoiseCompiler before creating directories or touching the destination. Serialization produces the same version-1 envelope with `packageVersion` and `resources`. Complete UTF-8 content is written to a unique sibling temporary file and forced to storage before atomic replacement of the selected target. Partial staging and pre-replacement failures leave an existing destination intact. Cleanup attempts to remove the temporary file and preserves the primary failure if cleanup also fails.

There is deliberately no non-atomic replacement fallback for resource packages. A filesystem/provider that rejects atomic replacement leaves the target alone and reports that another location is required. Parent directories created for a failed export can remain. Provider durability, directory-entry flush behavior, filesystem changes after the final path check and unusual network/permission conditions are not certified by source inspection.

Import requires an object envelope with an explicit integral `packageVersion` equal to 1 and an explicit object `resources`. Unknown outer fields, duplicate keys, unsupported/coerced versions and trailing JSON reject. The resource object passes through ProjectIO's strict complete format-2 reader, rather than filling omitted top-level data from Java defaults. Existing enabled-noise compilation and complete-candidate validation still occur in the owned Import workspace before publication. A failed read never opens that workspace or changes the destination project. The new `schema/resource-package.schema.json` records the existing envelope and references the canonical project schema; ContractGenerator emits it and the deferred drift/schema checks include it. This tightens malformed-package handling without changing valid version-1 serialized packages, UUID conflict rules or public engine/model API.

The file modal retains the entered path and export checkbox selection after failure, shows its error in a bounded-height scroll region, and remains available for correction/retry or Cancel/Escape. Opening a new package action clears its previous error. Package I/O does not save the project, change its path/dirty baseline/history, publish private Properties input, or change preview computation.
