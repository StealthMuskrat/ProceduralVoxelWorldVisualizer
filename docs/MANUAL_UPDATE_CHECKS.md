# Manual update checks and reviewed release links

Status: implemented on `codex/development-phase`, uncompiled and untested. Compilation, tests, native probes, independent replay, network checks and GitHub workflow execution remain deferred. No baseline pass count or release-acceptance gate is advanced.

Help > Check for Updates still opens User Settings > Performance when the active endpoint is empty. Otherwise it opens the dedicated results window and explicitly starts one request using the applied endpoint/allowlist. Repeated requests while running retain that request. Check Again retries only on an explicit action; Cancel Check invalidates it. Closing the results window cancels/clears its request/result, while collapsing keeps collection active without processing controls. Shutdown consumes the request owner before editor/background disposal. Nothing checks automatically at startup, edits private update settings, downloads application files or installs/replaces the application.

## Request and result ownership

UpdateCheckSession owns the exact applied endpoint and ordered allowlist values, a request token, one cancellable FutureTask and at most one immutable result. The worker receives an immutable validated configuration. Completion is queued to the UI and checks the original token and active configuration before publication. Cancellation, a new check, changed applied trust and shutdown invalidate queued late completions. Changing unrelated preferences or the project does not retarget the request. A newer active trust configuration requires an explicit new check; no implicit retry occurs. The production host uses its bounded existing editor executor and main-thread queue; rejected work becomes a recoverable result rather than an unchecked UI failure. Queue delivery and state access remain UI-thread responsibilities.

The results window shows the installed version and newer/current/older status. Comparison follows [Semantic Versioning 2.0.0](https://semver.org/): numeric core components have no machine-integer overflow, numeric prerelease identifiers precede textual ones, a normal release follows its prereleases and build metadata does not change precedence. Versions are limited to 256 ASCII characters and reject leading-zero numeric core/prerelease values. Desktop's About and update result use the same existing application-version constant; this does not bump the build version.

Open Release Information and Copy Release Link act only on the exact currently reviewed result object after checking current applied trust again. A value-equal replacement token has no authority. URLs are revalidated before publication: HTTPS, approved origin, no credentials/fragment, valid port and at most 4096 characters. Neither network completion nor merely showing the window opens a URL or copies text. Browser failure retains the reviewed result for retry and reports `UPDATE_LINK_FAILED` in the shared Application Error Center; browser integration being unavailable leaves Copy available. A reentrant Open is rejected. Check failures use `UPDATE_CHECK_FAILED` with bounded non-null descriptions. The production browser boundary uses Java Desktop BROWSE only on the explicit button; the Windows runtime already includes java.desktop. URL trust here means configured origin/TLS validation, not a guarantee about external page contents.

## Bounded transport and metadata

UpdateChecker retains its public check/parse signatures and version-1 metadata shape. The request uses default HTTPS certificate validation, an 8-second connect timeout and no redirects. A 12-second future wait covers headers and complete body receipt; timeout/interruption cancels the HTTP future and subscriber and shuts down the per-request client. Non-200 headers fail before body subscription consumes data. UpdateBody requests one batch at a time, rejects a batch exceeding the remaining 65536-byte allowance before copying it, cancels upstream on failure and ignores late delivery after completion/cancellation. Buffering overhead remains bounded; this is not a claim that there is only one physical copy of a body. UTF-8 decoding rejects malformed bytes instead of replacing them. Parsing rejects trailing/duplicate fields, unsupported/overflowing versions and non-text fields before interpreting the release.

The [release metadata schema](../schema/release-metadata.schema.json) and [controlled valid fixture](../fixtures/release-metadata.json) document the exact three-field envelope. Schema checks shape, version grammar, HTTPS string/URI representation and local length bounds; runtime checks credentials, ports and the configured origin allowlist. The fixture uses reserved example hosts and is never the application's default endpoint. It does not identify a real service to contact. User/App/Project formats, engine APIs, procedural results and saved projects remain independent.

Actual DNS/TLS/header/body deadline timing, cancellation under real transports, proxy/certificate policy, external browser/clipboard behavior and representative OS cleanup have not been exercised by this batch. The current direct network wait is bounded by the response-future deadline; this does not measure every platform's scheduling/cleanup latency.
