## Current controls before result publication

The manual checker previously installed release information or reported fetch failure from its queued UI callback. UpdateCheckSession now retains the validated request configuration and fetched metadata/failure in a one-slot CPU mailbox. Delivery only marks readiness: RUNNING, the request token and Cancel Check ownership remain stable, no result URL is exposed and no failure is reported yet. Invalid or null fetched metadata remains private until acceptance or cancellation.

UpdateCheckPanel captures the shown request and handles Cancel Check, Escape, Configure and the other current controls before accepting that same request after the window scope ends. Closing the results window cancels ready work before publication. Collapsing releases presentation controls while retaining the existing explicit-collection policy: an open collapsed host may accept a ready result after its native scope ends. A Configure callback that cancels and prepares a ready successor cannot authorize that successor from the old frame. Newly started inline work waits for a draw that owns its request. Successful checks need no additional confirmation.

Acceptance repeats the exact applied endpoint and ordered allowlist freshness check, then validates fetched release/version/URL data against the captured trusted configuration. Equal applied-value replacement and unrelated preferences remain independent. Changed trust retires the result and requires an explicit new check. Ready failures can be cancelled before reporting; accepted failures retain bounded original/secondary reporting and Check Again recovery. No frame automatically retries a failed, cancelled or stale request.

The request retains its FutureTask until acceptance or retirement, so readiness followed by a late handoff failure cannot silently expose an unaccepted result. An executor fault before acceptance similarly retires that preparation. If an owner explicitly publishes during an inline callback before a later poster/executor fault, the consumed result/report remains authoritative. Failure reporters may start a ready successor; original request capture and feedback guards prevent the older acceptance/report from consuming or contaminating it.

Cancellation, staleness, retry and shutdown clear the CPU mailbox independently of draining callbacks. Queued UI callbacks hold identifiers rather than fetched payloads/configuration. Retired workers cannot refill the slot; cooperative cancellation and transport cleanup retain their existing limits. Publication clears finished task/payload ownership, while reviewed immutable release information remains owned until a later request/cancel/close.

Open Release Information and Copy Release Link still require the exact current reviewed Result object and freshly checked active trust. A value-equal result from another request has no authority. Neither readiness, accepted publication, collapsed completion nor showing a window invokes those actions automatically. Browser/clipboard/configuration boundaries remain explicit and retain their existing retry/failure containment.

Trust parsing, HTTPS/origin/certificate rules, transport deadlines/body limits, semantic-version comparison, manual-only startup, metadata/configuration formats and headless model/engine APIs are unchanged. Update work never applies private Properties, changes document history, saves preferences or downloads/installs application files. This batch does not claim real HTTP/browser/clipboard behavior, physical input, DPI/OS, measured latency/heap or complete GUI acceptance. Other background completion paths retain separate policies.
