# Bookmark modal layout and decisions

Status: **uncompiled and untested** on `codex/development-phase` under the owner testing pause. This follows [bookmark input](BOOKMARK_INPUT_OWNERSHIP.md) and [bookmark ownership](BOOKMARK_DIALOG_OWNERSHIP.md). The validated baseline remains 922 tests / 120 suites.

Add Bookmark, Rename Bookmark and Teleport Coordinates now use a stable scrolling body and two measured persistent action rows: Apply/Cancel and Show Fields/Show Feedback. Each name/coordinate input fills the available body width beneath its label. Rename still shows read-only coordinates; 2D still has X/Z only and 3D/World has X/Y/Z. Candidate feedback remains bounded to eight Unicode-safe 1,024-codepoint previews with its original total count. It scrolls within the body instead of a fixed 110-pixel nested child. Long names, full raw inputs and stored diagnostics retain their existing limits.

All footer controls are collected before a decision. Cancel/Escape takes precedence over Apply or navigation. Field and footer IDs are scoped inside stable child/window identities to an exact document lifetime, BookmarkEditSession and current/stale target eligibility. Private edits, feedback browsing, magnification and unrelated revisions keep the same request IDs. Changed targets or same-UUID replacement documents invalidate the previous action context; the existing session still blocks stale publication and preserves its text. Explicit cancellation and each admitted opening release/replace presentation ownership. The scope grants no validation or transaction authority.

Show Fields reveals the first owned input; Show Feedback reveals the current attempt details. Failed parsing/displayed-buffer mismatch requests correction focus on the first affected field without accepting a fallback coordinate. Candidate rejection or runtime-only callback failure reveals feedback while retaining the same input, Add UUID and retry IDs. The new BookmarkEditSession.problemField method supplies only a correction target; complete displayed input and signed 32-bit all-axis parsing remain authoritative in Apply.

Completion captures the opening session. A navigation callback can explicitly cancel that opening and admit a successor before returning, including before throwing. Completion/error cleanup closes the predecessor popup without cancelling, clearing or attaching its error to the successor; the pending successor is presented on the next draw. Normal callback failure retains the original modal for retry and keeps the existing actionable log entry. Arbitrary callback side effects are still the callback’s responsibility. Toolbar picker/update/delete semantics remain unchanged.

BookmarkLayoutProbe defines sixty production layout receipts: Add/Rename/Teleport for each of three tabs across six wide/narrow/short/global/window combinations (54), plus a 300-diagnostic Add rejection at six combinations (6). Each form retains one opening across its magnification sequence, including the 6.25 font product. Receipts include work/modal/body rectangles, both footer rows, action/field IDs and scope version. Further native footer phases define Cancel/Escape before Apply, held Apply/Cancel across replacement openings, callback rejection/retry, success and error callbacks that admit a successor, unrelated edit merging, a held stale Rename, native correction of a lone sign, and explicit Add/Rename with one Undo/Redo each. Initial raw values, replacements, active source changes, validators and callback outcomes are fixtures; native controls make decisions and actual text events correct the final coordinate. Existing BookmarkInputProbe and the fourteen earlier document/session/displayed-input definitions remain queued. The new native context creates no GLFW/OpenGL or physical keyboard.
