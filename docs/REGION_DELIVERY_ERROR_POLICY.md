## Consistent host-delivery boundary

A directly thrown consumer Error previously bypassed the per-chunk Exception handler and terminated the whole region exceptionally with FAILED progress. The identical Error supplied through a failed acknowledgement was wrapped by CompletableFuture.join and became a DELIVERY failure governed by CONTINUE/FAIL_FAST. Errors while converting or registering observation on a host stage had the same inconsistency. This made failure policy depend on how the host expressed a fault.

ConsumerAcknowledgement.deliver now owns invocation and acknowledgement observation as one host boundary. RuntimeExceptions, including CancellationException, retain their existing control flow and identity. Other thrown host failures are wrapped in CompletionException, matching an exceptional acknowledgement's path. WorldContext uses the same existing per-chunk handler for the resulting delivery failure: increment failed once, retain the chunk/DELIVERY/original-message detail within the 1,024-detail cap, publish existing diagnostics, remove that pending request, and either continue or cancel remaining work. There is no automatic retry of consumer side effects. Direct throws, stage conversion, observer registration and future observation all pass through this boundary.

Successful generation and successful delivery remain separate. A failed delivery does not invalidate the complete immutable generated chunk or change its engine/cache result. A pending host acknowledgement still holds in-flight capacity until acknowledged or the stream withdraws its wait. The engine never completes or cancels a host stage and does not mutate its Error object, cause or suppressed list. If a stage invokes its observer then throws while registering it, registration failure is still a failed delivery; the host's already successful stage is unchanged.

An Error after the consumer explicitly cancels its stream records that attempted delivery as failed and leaves the remaining work cancelled, just as an ordinary exception did. Existing interrupted-wait flag preservation, host-stage cancellation, null/malformed-stage handling, cooperative cancellation checkpoints, stream-slot cleanup and observational completion futures remain in place. The boundary does not isolate or interrupt blocking host code. Internal generation/coordinator/profiler/cleanup faults outside host delivery keep their existing paths; this is no promise of recovery from an unusable VM.

Public method signatures, record shapes, request defaults, serializers, registries, schemas, chunk arithmetic and editor/native dependencies are unchanged. ChunkConsumer Javadoc now states the common thrown-fault/failed-stage policy. The existing consumer-stage note's earlier direct-Error terminal behavior is superseded by this follow-up.
