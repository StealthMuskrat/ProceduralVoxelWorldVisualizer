## Recoverable task and callback faults

The manual update worker used FutureTask, which captures thrown failures. A fetcher Error or a rejected UI handoff could therefore leave the session RUNNING indefinitely, with no queued publication capable of ending it. Scheduler Errors escaped the UI boundary, while browser/clipboard Errors and error-notification callback faults could escape the result dialog.

The fetcher now captures thrown failures for the ordinary queued UI publication path. Normal successful and failed fetch outcomes still wait for that queue; a finished worker does not publish a result directly. During UI-thread refresh, a terminal FutureTask is inspected only for exceptional exit or cancellation. An exceptional UI handoff retires the request token and becomes a visible retryable FAILED state. A task cancelled by its executor becomes CANCELLED. No fetch, browser action or retry starts implicitly. Pending network work is never awaited on the UI thread; terminal task inspection does not wait for fetch completion. A queue implementation that silently discards an accepted callback still violates the supplied dispatcher contract and is not detected by this fallback.

Applied trust freshness is checked before terminal-task fallback. Cancelled, stale and closed owners discard obsolete task faults; callbacks queued before a handoff throws cannot publish after retirement. The production panel also cancels before observing the task when its host already marks the window hidden. Scheduler failures retire only a still-running request whose submission failed, preserving a successor started reentrantly by an older callback. A poster or executor fault after inline terminal UI publication does not replace that published success/failure or report it twice. If an executor throws after running the task inline, start still returns false for that rejection while retaining the already published state.

Check failure reporting and browser/clipboard/configuration action reporting now contain thrown callback failures. The original bounded message remains visible; if the Error Center callback also fails, local feedback includes a bounded secondary notification detail without recursively reporting it. Throwable message extraction has a class-name fallback if getMessage itself fails or has no usable text. These paths do not mutate caller-owned failure objects. A reporter that starts, cancels or closes another request cannot attach the predecessor's feedback to that new owner.

A failed release-link or configuration callback retains the exact reviewed result, native retry identities and explicit Copy/Open/Configure actions. Existing result/configuration checks still govern every link action. Opening remains guarded against reentry and releases that guard in finally, including on an Error. Context closure, request replacement and Escape/collapse/held-input rules keep their existing ownership. Callback side effects are not rolled back, and blocking callbacks remain cooperative; no new executor or callback-preemption guarantee is introduced.

Trust parsing, certificate/origin rules, transport deadlines/body limits, manual-only startup behavior and release-version comparison are unchanged. No automatic download/install, endpoint default, serializer, schema, project/user/app format, engine/model API or dependency is added. The existing constructor/host queue contract is preserved. Primary and secondary feedback is bounded to fewer than 2,200 UTF-16 code units; normal single-fault feedback retains its previous bound.
