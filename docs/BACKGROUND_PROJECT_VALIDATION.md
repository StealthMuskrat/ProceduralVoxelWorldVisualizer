# Background committed-project validation

Status: **uncompiled and untested** on main under the owner's development-phase testing pause. This implements the interactive Tree 18.2.6 validation path with Tree 4.4 responsiveness and existing diagnostic ownership. The last observed baseline remains 922 tests / 120 suites. No compiler, JUnit, native probe, independent client, Python checker, schema generator/validator or GitHub workflow ran.

## Interactive behavior and ownership

View > Validate Project and the Validation Results footer now request background validation instead of compiling the project synchronously on the UI thread. The editor copies committed data into an owned snapshot, schedules NoiseCompiler.validate through its existing bounded background executor, and publishes the resulting immutable diagnostics through the UI queue. Snapshot copying and final source-value comparison still run on the UI thread; this does not claim zero UI cost or measured responsiveness for arbitrarily large documents.

The window displays the request state and retains previous results while Running. Its first footer action becomes Cancel Validation. Cancellation immediately retires publication authority and requests interruption, removing a queued task from the ordinary editor executor where possible. A compiler already running may finish its isolated work; it cannot publish after cancellation. Explicit retry creates a new request. Hiding the results window leaves an explicitly requested check running; editor shutdown retires it before background/engine cleanup. One active validation request is admitted per editor. Existing preview scheduling/memory budgets are unchanged.

A result belongs to its document lifetime, committed model identity/revision, source values and the diagnostic list/scope present when validation started. Ordinary edits, Undo/Redo, New/Open or a newer rejected-edit diagnostic publication retire the older check. Before publication, complete committed values and diagnostic contents are also compared, catching in-place unversioned mutation. Cheap identity checks run during UI refresh; full serialization is not repeated each frame. Ready status becomes stale after a later ordinary project/result change. Properties draft changes, selection and user preferences do not cancel a committed check when its source and diagnostic publication remain current. Snapshot-only results never Apply private input, save a file, dirty the project, create history or replace the runtime engine.

Worker exceptions and Errors publish failures only on the UI thread. Scheduling rejection and exceptional UI handoff are recoverable; polling a completed FutureTask surfaces a handoff failure even when no callback could reach the queue. A successful task still awaits its UI callback. Enqueue-then-reject handoffs lose publication authority, and stale callbacks cannot overwrite a retry. Reporting failures are contained; a reporter may explicitly start a successor without the old request retiring it. Explicit worker cancellation is observed without a queued result. The compiler's normal numeric/validation policies remain unchanged.

The existing synchronous EditorState.validateProject method remains available for direct callers and retires an outstanding interactive request before publishing. Both paths use one immutable diagnostic-publication method. The production menu and footer use the background path. Copy/Go To Problem keep their exact displayed-row ownership. Start/Cancel have separate presentation scope tied to the diagnostic publication, request token, document lifetime and revision, preventing held controls from adopting replacement results or switching from Cancel to Start on release. The existing three-action footer and clipped result layout remain.

Central Help includes a searchable background validation guide, the Validate menu routes directly to it, and the diagnostics topic links it. There are no project/preference/schema/registry/default or public headless API changes.
