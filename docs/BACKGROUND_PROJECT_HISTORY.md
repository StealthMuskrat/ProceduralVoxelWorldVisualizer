## Prepare the captured history entry outside the UI action

Desktop's Edit menu and configured project-history shortcuts now use a background ProjectHistoryPanel/Session. An unchanged Properties draft starts preparation directly. Modified Properties values or retained raw seed text still require Discard Draft and Undo/Redo or Cancel first. Discard authorizes the requested history step; it does not apply the draft or immediately throw it away. While preparation runs, current committed values and private input remain active.

DocumentSession adds requestUndo()/requestRedo(), HistoryRequest.prepare(), immutable PreparedHistory.success()/diagnostics(), currentHistory(result) and applyHistory(result). Capture, inspection against the live owner and publication belong to the owner thread; preparation may run on a worker. Empty-direction capture rejects without scheduling work. Existing public void undo()/redo() retain their synchronous behavior, including harmless empty-direction calls.

The request owns the exact captured delta, source values and validation policy. A worker reconstructs the history candidate from those private values, runs the captured validator and copies accepted values so later mutation of a retained validation input cannot change the completed candidate. No mutable candidate accessor escapes. Validation callbacks must not read or mutate the live document or concurrently change their inputs. Rejection owns an immutable diagnostic list without moving either stack.

currentHistory can check accepted or rejected work without validation or consumption. It verifies the same document, unconsumed result, exact source object/JSON, document lifetime, validation function identity, path/checkpoint/receipt, both history heads, history-byte count and captured source delta. An identical later Save receipt or an Undo/Redo round trip supersedes the old capture. applyHistory repeats these checks, consumes an accepted result once, moves exactly the captured delta between stacks and installs its candidate. Total history byte accounting remains unchanged. No new edit is inserted and no rejected entry is skipped.

## Keep the decision cancellable until publication

The history modal now also shows preparation progress for clean requests. Its existing first action is disabled and displays Preparing Undo/Redo while the existing Cancel action and Escape remain active. The same two action identities and persistent footer layout are retained. Duplicate shortcuts or Discard releases cannot schedule another task for the pending direction. Source/project/file gates continue to treat the history request as busy.

Each FutureTask and opaque work identity belongs to the UI session. Worker completion waits for queued UI delivery. Cancel, clear/New/Open coordination and lifecycle closure retire that identity, cancel/remove queued work where supported and preserve current private input. A non-cooperative worker may finish later, but cannot move history or clear another controller/request.

Before adoption, the UI checks project lifetime/object/revision and complete committed values, saved path/dirty baseline, selected UUID/siblings, exact Properties draft object/values and raw seed ledger. It repeats the current private/project-action blocker and ownership checks after that callback. Reentrant cancellation or a successor request cannot be consumed by the older completion. The model's currentHistory check also rejects changed policy, checkpoint or stack authority before presenting a rejected result or moving a successful one.

Successful completion retires the confirmation before publication and keeps the existing movement fence through model application and selection reconciliation. Only then does the private draft refresh/discard take effect. Deleted selection and seed ownership are cleared through the existing reconciler. A failing refresh after a completed model step reports the completed status without replaying or rolling it back. Failed validation, scheduling, worker or UI handoff ends preparation, preserves the stacks/draft and reports bounded feedback; the user requests Undo/Redo again explicitly. There is no automatic retry or skip.

Central Undo/Redo menu Help and history-button context Help describe the same background/discard/cancellation rule. Legacy synchronous controller constructors remain for isolated direct workflows. The prepared API is additive and headless; project format 2, schemas, registry versions, shortcut bindings/preferences, local curve/text history and generated scalar/voxel semantics are unchanged.
