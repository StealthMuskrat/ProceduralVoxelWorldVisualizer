# Volume self-shadowing — implementation awaiting validation

GitHub testing is deferred by the owner until the program is fully developed. This document describes the development implementation and its planned checks; it is not passing test evidence. The last validated main build remains the directional mesh-shadow baseline.

User Settings > Visualization adds opt-in Volume self-shadowing and 8, 16 or 32 light-ray samples. Historical User Config v1 files default to disabled with 16 samples. Both new fields are optional in the current schema so historical files remain valid; older readers that reject unknown fields require an update. The strict reader rejects null/coerced values and unsupported step counts. Mesh directional shadows remain a separate control. Unlit bypasses volume attenuation.

For each contributing view-ray sample, a secondary ray travels towards the existing normalized `(0.4,1,0.3)` light until it exits the accepted volume cube. Midpoint samples use the same encoded density texture, threshold and finite display transfer as the view ray. Optical density is `clamp(mapped density,0,1) * opacity per block`; transmittance is `exp(-integrated optical density)`. Palette emission is multiplied by `0.35 + 0.65 * light transmittance`. The ambient fraction stays visible, and view-ray extinction/background transmission keep their existing meanings.

This is a display approximation over the resident scalar texture. It is not a global volumetric transport solver: unloaded volume, external triangle occluders, multiple scattering, colored light transmission and anisotropic scattering are not represented. Density clipping, interpolation and the display threshold define the medium used for attenuation. The light direction and ambient/direct fractions match the existing mesh lighting convention.

The inner shader loop is capped at 32 samples and the existing view loop at 512, at most 16,384 additional density fetches per pixel. Disabled/unlit, zero-opacity and noncontributing view samples avoid the inner work. No depth map, auxiliary scalar texture, CPU field sampling or upload is introduced by a lighting change. GPU_DRAW includes the secondary rays when profiling is active. Extra work can be substantial on software/low-end GPUs; no hardware performance claim is made. This feature remains off by default.

Both fixed analysis and moving streamed windows use their currently accepted texture/encoding/origin. User lighting preferences do not enter source compilation, window keys or authored ProjectData. Changing the toggle, sample count or Unlit should preserve accepted texture identity/version, source generation/submission stamp, upload counters and project/history. Existing upload/pressure/overlap semantics remain in force; the implementation does not add coarser volume sampling or sparse residency.

`VolumeLight` supplies a pure CPU reference over encoded trilinear/edge-clamped values and a checked immutable settings record. `VolumeData.interpolate` retains its previous decoded behavior through an extracted encoded interpolation helper. Existing volume rendering overloads and default appearance remain available. No engine/model/archive API gains a native dependency.

Deferred test definitions cover homogeneous Beer–Lambert attenuation, each limiting cube face, zero/threshold/disabled/boundary cases, an independent piecewise affine antiderivative, extreme canonical encodings, strict historical preferences and project isolation. Native normal/strict-3.0 probes and independent Python reference definitions cover light quality, Unlit, thresholds, extreme scaling, a clamped gradient, opacity zero and fixed/streamed control-only ownership. These definitions have not been executed for this batch. Full GUI, hardware performance and Windows 11 acceptance remain separate.

The unvalidated [display-detail extension](VOLUME_DISPLAY_DETAIL.md) carries physical sample spacing through both the view-ray box and the CPU/GPU light path, so attenuation uses world distance independently of texture dimensions.
