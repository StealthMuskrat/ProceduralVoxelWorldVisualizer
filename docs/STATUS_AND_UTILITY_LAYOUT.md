# Reserved status strip and bounded utility windows

Status: implemented on `codex/development-phase`, **uncompiled and untested**. Compilation, regression/native execution, independent replay and GitHub testing remain paused by owner instruction. No previous pass count or acceptance gate advances.

## Dock and status geometry

The fixed 28-unit status overlay is replaced by an explicit split of the main ImGui viewport's work rectangle. After the main menu, `StatusBarPanel.prepare` measures the current global font, frame height, action labels and spacing. `StatusBarLayout` rounds inside the work rectangle to whole coordinate units, reserves a bottom strip, and gives the remaining top rectangle to the dock host. The dock bottom and status top meet exactly. The default docking builder now accepts that actual rectangle's dimensions; its old hard-coded 26-unit height deduction is removed.

`DockWorkspace` mirrors the pinned native DockSpaceOverViewport host name, flags, style and `GetID("DockSpace")` identity, while supplying the reserved rectangle rather than the full viewport work size. Existing docking node/window associations and saved INI can therefore retain their IDs. It uses the public binding's DockSpace call, without modifying viewport/internal work offsets or keeping a native pointer. The exact native submodule shipped by imgui-java v1.89.0 is [1d8e48c161370c37628c4f37f3f87cb19fbcb723](https://github.com/ocornut/imgui/blob/1d8e48c161370c37628c4f37f3f87cb19fbcb723/imgui.cpp); the submodule identifies itself as native 1.89.9. The [binding](https://github.com/SpaiR/imgui-java/blob/v1.89.0/imgui-binding/src/main/java/imgui/ImGui.java) remains pinned to imgui-java 1.89.0.

The status strip is attached to the bottom of the main application work rectangle. A wide strip has the concise status at left, Settings next to the right-side notifications action, and notifications at the far right. Narrow strips put status on a separate first row and keep actions on the second. Labels progress from `Notifications` to `Notices` to `N` (or `!` when action is required) plus the unread count; a hover description retains exact unread and action-required counts. Settings can use `...` with its full tooltip. Native `###` IDs remain stable across label changes. Action hit rectangles remain inside the strip; at widths too small for both actions, notifications get priority. Menu/shortcut Settings routes remain available. Extremely small native areas may not fit even a font/control, so full visual usability is not promised there.

Status presentation replaces CR/LF/tab with spaces, reads only a bounded code-point prefix, and uses a clipping rectangle rather than pushing actions beyond the window. The visible prefix is at most 120 source code points plus an ellipsis, and the hover prefix is at most 2,048 plus an ellipsis. Valid surrogate pairs are not split. Null/empty status displays Ready. Original `state.status` and complete log/notification messages are unchanged. The strip remains a status/action area, without new performance graphs or polling.

Clicking Settings follows the existing User Settings route. Clicking notifications opens the existing production Notifications panel. Opening does not mark entries read, clear action-required state or choose an event. Neither action changes project/history or publishes a private draft. Counts are captured during preparation; an event emitted later that frame can appear in the next frame's counts. No engine/model, schema, registry, generator or public API change is needed for this transient layout.

## Utility window adoption

Thirteen additional presentations adopt the [floating window policy](CURVE_LAYOUT.md): Find, Logs & Error Center, Notifications, Validation Results, Profiler, Themes, Check for Updates, Help, About, and the four User Settings/Project Settings/Application Settings/Debug & Profiling windows. Each actual Begin is observed, including collapsed/closed Begin results; existing content lifetime/close/cancel guards remain in place. Settings keeps independent geometry per logical page. About gains a 680 x 350 FirstUseEver size; other preferred sizes remain as before.

The helper honors the first native INI observation, keeps valid user bounds stable, skips dock-node sizing/collapsed-height replacement, and defers correction during held mouse buttons. Relative main-client coordinates and absolute backend monitor work areas remain separate; live detached windows with no monitor data do not fit repeatedly inside their own client area. Native wrappers are resolved locally. Existing workspace capture still owns preference persistence. These outer-bound changes do not redesign every utility's internal list/action rows or reset private editors, searches, theme previews, update requests or profiler export reviews.

The reserved dock rectangle does not mutate the viewport's global WorkPos/WorkSize. Floating tools and modals can still cover the strip like other application windows; their main-client fitting policy uses the original work rectangle. Independent physical monitor intersection for all popups, internal utility reflow, per-monitor font/atlas/style metrics, minimized/tiny-frame behavior and full GUI/Windows 11 acceptance remain pending. This is not a full specification 4.1.4/4.3 or A32 certification.

Core panels and Voxel Manager/Inspector have a separate [outer-bounds and responsive XYZ follow-up](CORE_WINDOW_LAYOUT.md).

## Deferred definitions

Twelve `StatusBarLayoutTest` definitions provide analytical wide/narrow rows, notification/settings compact variants, notification hit-space priority, fractional pixel alignment, negative origins, one-pixel/tiny heights, immutable/invalid metric shapes, code-point/text bounds and finite extreme metrics. No JNI is used by those definitions.

`StatusBarProbe` first creates a legacy DockSpaceOverViewport INI with three explicitly documented placeholder dock windows. A fresh context loads it and submits the real new dock host/status panel, requiring the identical native dock ID and retained associations. Four cases cover 1280 x 720/global 1, 360 x 240/global 2.5, 480 x 320/global .5, and a second fresh-context INI restoration at 800 x 600/global 1. It measures native action/bar bounds, checks that docked placeholders remain above the strip, clicks both production strip actions, opens the actual Notifications panel and checks that its floating bounds recover into the client work area. Exact action counts, unread state, private Properties/raw seed, original status, preferences and project/history are retained. `scripts/verify_status_bar.py` independently checks case dimensions/scales/row modes, dock/bar partition and far-right hit bounds plus the ownership receipts.

Future Linux/Windows steps/artifacts are wired with unchanged development trigger exclusions. None has run. The probe has no renderer, GLFW platform window or real detached monitor; physical detached and DPI flags are explicitly false. It does not render the three production resource/property/visualizer contents or all thirteen utility routes, test every status tooltip/keyboard combination, or certify hardware monitor behavior. All existing native definitions remain queued for later full validation.

The subsequent unvalidated [Help/context/About batch](HELP_AND_ABOUT.md) replaces their inline contents with retained scrolling presentations and persistent actions, adds canonical topic/options/related search and explicit context routing, and updates first-use sizes while retaining Help/About window identities and saved geometry ownership. Full physical/input acceptance remains separate.
