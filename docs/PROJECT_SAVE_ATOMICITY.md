## Publication and saved checkpoint

ProjectIO previously retried an unsupported atomic move with a non-atomic replacement. That fallback could sacrifice the previous destination if replacement failed partway through. It also deleted the temporary path after a successful move, allowing an unnecessary cleanup error to report failure after publication. DocumentSession serialized the active document again after saving rather than retaining the payload actually written.

ProjectIO now validates and serializes before filesystem admission, writes a temporary sibling, forces and closes its file channel, and requests atomic replacement. AtomicMoveNotSupportedException becomes an IOException with guidance to choose another location; no non-atomic fallback is attempted, including for a new destination. Failed staging or publication attempts delete the temporary sibling. An IOException during deletion is suppressed on the primary IOException, RuntimeException or Error rather than replacing it; cleanup failure can leave an unpublished temporary file. Successful replacement transfers ownership of the temporary file and performs no subsequent filesystem cleanup.

The exact serialized payload is returned internally to DocumentSession and becomes its saved checkpoint only after publication succeeds. Save failure leaves the session path, checkpoint, active identity, session token and Undo/Redo accounting alone. Saving retains document lifetime and transaction history. If the source is changed at the injected I/O boundary, the later value remains dirty because it was not the payload written. This deterministic boundary case does not establish concurrent document access: callers must still serialize document edits and saves, and custom validators must not mutate the document.

Public no-argument constructors, ProjectIO.save and DocumentSession.save signatures are retained. ProjectSaveFiles and the injected constructors/checkpoint method are package-private, per-instance boundaries over JDK file operations, without mutable global hooks. Project format 2, JSON encoding, UUID references, sparse overrides, headless dependencies and explicit Save remain unchanged. Locations without atomic replacement are now explicitly unsupported for project saves. Flushing a file and requesting an atomic move do not establish directory synchronization, crash/power-loss durability or guarantees beyond the filesystem provider; those require later platform evidence.
