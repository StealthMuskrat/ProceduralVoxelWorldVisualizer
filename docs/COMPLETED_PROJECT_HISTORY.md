## Complete worker return before moving a history step

ProjectHistorySession already retained a prepared Undo/Redo candidate or captured validation failure until the current history controls permitted acceptance. Its readiness callback still dropped the task handle. That could authorize movement inside unfinished posting or before executor.execute returned successfully, and conceal a subsequent handoff/admission failure.

The callback now only marks readiness and retains the task handle. Acceptance requires readiness, normal complete worker return and successful executor admission before taking the mailbox. Inline acceptance during posting or between inline task execution and successful admission leaves request/work versions, project, private Properties input, raw seed ledger, preferences, revision and both history stacks unchanged. Later ordinary owner acceptance finishes the original action without another confirmation or automatic retry.

Captured validation failures and rejected history candidates wait for the same complete boundary before preparation feedback. A poster/admission failure cannot hide behind an unaccepted value or captured failure. Operational Future status/get faults retain their existing refresh recovery policy; not every operational fault waits for Cancel. The shared nonblocking completion helper contains terminal status/get faults and restores interrupted-read interruption.

## Original-request observation and retirement

Refresh captures its original work token before observing the Future. Acceptance retains that identity through refresh and repeats the complete-worker check before taking a payload. Either terminal read may create a ready replacement and return normally, throw Error or report cancellation; the old observation cannot consume or fail that replacement.

Retirement returns the identity reserved before cancellation callbacks. Staleness and preparation failure check that identity before assigning status or reporting an error. Failure feedback checks again after describing the Throwable, so a message getter may create a ready explicit retry or close the controller without obsolete feedback overwriting that outcome. Public clear remains a void operation; request/dialog/work identity policies are unchanged.

Final history publication enters the existing movement fence before retiring the completed task. Cancellation callbacks therefore cannot start another Undo/Redo between consuming authority and applying the prepared step. Publication also checks the reserved retirement identity and closed state before installing the candidate. If cleanup closes or retires the owner, the old movement cannot continue. Final close marks the controller closed before cancellation, preventing cancellation-driven admission into a closed controller.

The movement fence still spans document installation, selection reconciliation and consumed refresh-failure reporting. Those consumed failures retain their existing reporting, revision and single-use behavior. A successful history step cannot replay after refresh failure; a later movement needs a new explicit request.
