## Callback claims and finite listener faults

CancellationToken previously copied raw callbacks for dispatch. Closing a registration after that snapshot could not suppress a callback that had not started. An Error from one listener also aborted the loop, leaving later listeners unattempted, including engine subscribers waiting for queued cancellation.

Each registration now owns an atomic pending callback. Dispatch claims and clears that reference before invoking it. Close clears the same reference and detaches the entry, so it can suppress a captured callback that has not been claimed. Close remains nonblocking and does not stop or wait for an already claimed callback. Equal Runnable objects still get independent registrations; callback order remains unspecified. Close/claim clears the stored callback reference even while the caller retains the registration handle.

Explicit cancel still sets the cancellation flag once, snapshots/clears the registry and invokes outside its lock on the cancelling thread. Registered RuntimeExceptions retain their existing ignored behavior. Listener Errors are retained while the remaining eligible callbacks are attempted; the first encountered Error is rethrown with later Errors suppressed unless they are that same Error object. The token remains cancelled and repeated cancel does not replay callbacks. A callback registered after observed cancellation still runs inline on the registering thread and propagates its failure. Parent suppliers remain polled; observing a parent does not drain callbacks registered earlier.

WorldContext now contains a parent's RuntimeException or Error at all three admitted-subscriber boundaries: cancellation registration, shared-generation activity polling and terminal publication. The offending future completes exceptionally while healthy subscribers can keep shared work and receive the complete immutable chunk. Registration failure retires its pending ownership before queue admission is reconsidered. Initial validation/parent checks before admission can still throw synchronously. Generation failures themselves keep their existing shared-result semantics; these changes do not turn them into per-subscriber successes.

Public signatures, queue/cache policy, project/schema formats, arithmetic and UI/preferences are unchanged. Host callbacks/suppliers remain cooperative; this change does not preempt a blocking callback or establish VM-failure guarantees. Error definitions use finite AssertionErrors, rather than evidence of recovery from exhausted VM resources.
