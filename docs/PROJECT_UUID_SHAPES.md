## Model fields and user map keys

ProjectIO previously inferred UUID values from JSON key spelling anywhere in a document. A legal expression input called uuid, reference or targetUuid holds a Binding object, so this scan could reject an otherwise valid saved project. Conversely, UUID elements in membership arrays, folder childOrder and project rootOrder did not receive the same full-text preflight before model binding.

The package-private ProjectUuidShapes visitor now follows declared public model field types, including inherited fields, lists and map value types. Cached class metadata is immutable. User map keys are preserved; Binding objects beneath those keys still validate their real UUID fields. Declared UUID text must use the full 8-4-4-4-12 hyphenated hexadecimal spelling, with either hex case accepted. UUID collection elements reject null, non-string and alternative textual forms before binding, with their exact escaped/indexed JSON path. Optional scalar null references retain existing semantics; normal model validation still enforces required identities/references, uniqueness and ownership.

Sparse operation overrides are visited as Settings. Known embedded curve parameters are visited as Curve/Point definitions, and the existing processing noiseGeneratorUuid parameter retains its explicit reference meaning. Other JsonNode parameter/value payloads remain the responsibility of their declared semantic validators, rather than acquiring UUID meaning from arbitrary user keys. Unknown model fields still reject during binding.

SettingsResolver checks the merged, owned Settings JSON before UUID conversion, preventing direct edit/save paths from committing a raw override representation that strict loading would later reject. Validator also applies the shared lexical rule to raw curve identities and processing-reference parameters. No check trims, repairs or invents identities. ResourceGraph reference discovery now descends through object-valued input entries named uuid or childOrder, while scalar own UUIDs and organizational child-order arrays remain metadata. Dependency-aware selection, dependent reviews and replacement deletion therefore retain those procedural links.

Public signatures, UUID values, sparse inheritance, project format 2, the existing schema UUID formats and headless dependencies remain unchanged. Parsing still uses the complete-document boundary. Base64/shortened or otherwise nonconforming serialized UUIDs are not alternative project formats. The visitor is UUID preflight, not a replacement for full model/compiler/schema validation.
