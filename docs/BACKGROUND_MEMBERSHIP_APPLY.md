## Prepare the member transaction without replacing private Properties

Desktop's background PropertyPanel now opens a background MembershipDialog. Apply Members captures the ordered temporary checkbox selection and a DocumentSession prepared edit. Its bounded editor worker copies the owned committed project, changes only the selected voxel set/group's member list, runs the captured full-project validation policy, freezes accepted values and builds the structural Undo delta. Worker code never reads live EditorState or native controls. Current committed members, the existing Properties draft and generated previews remain active until queued owner-thread publication.

Success commits one document edit, advances editor revision and copies only the published member list into the existing Properties draft. The draft object, its unrelated private ID and raw input ledger remain intact. The private member list is a separate copy of the committed list. If a custom successful validation policy changes members, the published member values are authoritative for that copy. A postpublication private-refresh failure reports the committed status and consumes the session without replaying the transaction. Saving and preferences remain explicit and independent.

Voxel sets participate in generation predicates; voxel groups organize resources. Empty membership is valid. UUID order and duplicate-free checkbox behavior retain their existing semantics. The public direct MembershipEditSession and MembershipDialog constructors remain synchronous, while production PropertyPanel passes its configured worker/UI handoff. No engine/model API, project format 2, schema, registry or scalar/voxel rules change; the batch reuses prepared document edits.

## Preserve temporary choices and exact publication authority

Opening ownership still includes the exact editor, document lifetime, project UUID, selected membership/kind/sibling list, Properties draft object and full opening active/draft membership values. Unrelated committed catalog edits and their history movements before Apply remain allowed when those membership owners and selected types remain valid. Apply captures the current complete document and private state at that moment. Changes during preparation supersede that captured work; a still-current membership session can be reviewed and explicitly applied again against the newer catalog.

The work owner checks exact committed/private values, document lifetime/object/revision, selected UUID/siblings, raw input ledger and saved path/dirty baseline. Prepared-document authority additionally covers validation-policy identity, saved checkpoint/receipt and Undo/Redo heads/bytes. An identical second successful Save supersedes already prepared work. Both accepted and rejected results must pass currentEdit. Shared diagnostic identity, copied values and scope prevent an older member attempt from overwriting newer validation results.

The worker request owns an immutable ordered UUID selection. Checkbox and Select/Clear Matching changes retire pending Apply and keep the newly chosen selection, even if a later toggle restores the same final values. An unchanged checkbox notification does not retire work. Duplicate Apply cannot schedule another task. No older completion can overwrite new choices, a changed owner, a reopened dialog or a disposed panel.

## Responsive controls and explicit correction

During preparation the footer displays Applying Members... and disables Apply. Cancel/Escape stays active; filter, Issues/Members, Selected Only and choice controls remain available. Work transitions change footer gesture ownership while row identities remain stable during the same dialog. A checkbox change and work completion cannot turn an old held footer release into a new Apply phase. Cancellation keeps priority over other footer actions.

Compiler rejection retains the temporary choices, complete diagnostic count and up to 256 immutable attempt diagnostics; the Issues page continues drawing at most eight bounded details. A changed choice clears old attempt feedback. Scheduling, worker, externally cancelled-task and UI-handoff failures release Applying, clear earlier candidate details, retain the selection and report bounded MEMBERSHIP_APPLY_FAILED feedback. Apply Members explicitly retries. There is no automatic resubmission.

Cancel/close and PropertyPanel lifecycle closure invalidate the opaque identity, cancel/remove queued work where supported and preserve the parent draft/document. Non-cooperative or already completed workers can finish later but cannot apply into a successor or disposed panel. The production Edit Members button has centralized context Help describing member-only publication, cancellation, retry and the set/group distinction.
