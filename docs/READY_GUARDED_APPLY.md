# Ready-result cancellation for guarded Apply

Development implementation on main; **uncompiled and untested** under the owner's testing pause. No compiler, Gradle, JUnit, native probe, consumer, Python/schema checker or GitHub workflow ran. The observed baseline remains **922 tests / 120 suites**. Trees 3.1/4.4/18.1/18.7/19.6 and A03/A22/A32 retain their recorded partial/pending status.

## Delivery and acceptance are separate

Source-link, Find, property-reference and resource-browser selection guards already prepare explicit Properties Apply on workers. Their UI delivery previously also published the transaction and installed/revealed its destination, which let frame-start delivery run before a ready frame's modal Cancel/Escape. SearchNavigation and ResourceSelectionSession now keep an owned CPU mailbox and explicit delivered-ready state. Delivery grants no project publication or navigation authority.

NavigationGuardDialog renders and processes its controls, unwinds the popup and dispatches Cancel/Escape before asking its owner to accept prepared work. Source/Find/reference hosts share the navigator-aware presentation path; ResourcePanel supplies its selection acceptance path for tree/range/empty/Voxel Manager decisions. The ready result remains pending/preparing, so duplicate Apply/Discard requests stay blocked and Cancel stays enabled. Readiness changes neither work version nor native decision identity; a Cancel press spanning delivery can release onto the same action.

Acceptance is tied to the work version shown by that modal as well as its exact decision opening/frame. If explanation/action/completion callbacks retire work or admit a successor, the old modal cannot accept that successor's result. A normal successful Apply still finishes from its original explicit action; no second confirmation is introduced. Only a displayed decision path can request acceptance. The existing owner guards recheck complete source/private/raw/selection/checkpoint/history/policy/diagnostic and destination authority before publication, around source/blocker callbacks and before navigation/selection. Updating active source, raw seed generation, shared diagnostics, path/checkpoint or validation policy after delivery still retires old work.

Successful Apply consumes before private refresh and terminal callbacks. It remains one project Undo transaction, with navigation/selection outside history. A removed destination, later stale source or reveal/installation failure keeps that accepted edit and cannot replay it. User preferences, explicit project Save, generation and headless APIs remain separate. Public synchronous constructors retain their original behavior; internal asynchronous owners now call acceptPrepared after their control decision.

## Cancellation, failure and retained memory

Cancel, Escape, close and supersession invalidate both queued and ready CPU ownership. Late workers cannot repopulate the retired mailbox. UI delivery closures carry request identifiers and immutable destination data rather than the prepared candidate, so retired completed projects are released independently of when an old queued callback is eventually drained. Current work retains one prepared payload; a cancelled worker may keep its own inputs until it exits. Cancellation remains best effort and does not interrupt every compiler phase.

A ready rejected/failed result remains cancellable before its feedback is installed. Current acceptance installs immutable rejection details or bounded failure feedback and retains explicit retry; unchanged frames do not retry. Queue/handoff/external Future faults retain existing recovery. Duplicate old deliveries cannot populate or consume successor work. Terminal callback failure remains contained after consumption. Final closure clears the mailbox; native scope cleanup happens after prepared publication has returned.

This does not move owner snapshot capture, full comparisons, diagnostics presentation, target resolution, document history publication or draft/reveal work off the UI thread. It does not change readiness/publication policy for unrelated background operations or promise measured latency, memory pressure, physical input, DPI/OS or complete Windows 11 acceptance.
