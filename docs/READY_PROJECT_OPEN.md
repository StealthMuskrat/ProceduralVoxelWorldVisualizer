## Current loading controls before replacing the document

ProjectFileWorkflow previously installed a prepared Open candidate or reported its rejection during queued UI delivery, before the loading modal handled current Cancel Open/Escape. It now retains the candidate or captured preparation failure in a one-slot CPU mailbox. Delivery only marks readiness: phase LOADING and the attempt generation remain stable, the current project/lifetime/history/checkpoint/selection/private input remain active, and candidate diagnostics or fatal preparation errors have no publication authority yet.

ProjectFileDialog captures the loading request and original attempt before drawing. Current Cancel Open/Escape runs first; after the native popup scope ends, acceptance requires the same active dialog ticket, phase, request version and attempt. Loading control IDs include that attempt while remaining stable across readiness. A path submission that prepares inline cannot be accepted as the previously shown path dialog; a later loading draw owns its new attempt. A supplied startup filename can prepare before any native frame, but delivery alone cannot install it. The first current loading draw still decides cancellation before acceptance. An unavailable popup does not accept for absent controls.

Acceptance compares exact displayed/submitted path text, including Unicode, spaces and equivalent but differently spelled paths. It repeats complete ProjectFileOwner document/source/private/raw/selection/saved-path/dirty authority and current transition blockers. Those checks run again after presentation callbacks. An unavailable opening or changed owner retires old work and requires an explicit new request; a callback-created ready successor cannot be consumed or retired by the older acceptance. No frame retries automatically.

The original Open finishes without another confirmation when accepted. DocumentSession.applyOpen still validates its captured document identity/lifetime/path/checkpoint and validator policy, consumes one candidate, establishes the prepared saved checkpoint, creates a new document lifetime and clears history. The UI then clears selection/private/raw/diagnostic state and refreshes the resource UI once. Compiler validation is not repeated at installation. Prepared inputs are privately owned; Open does not write or modify the incoming file.

Ready success, malformed input, rejected validation and captured compiler failure may all be cancelled before replacement or primary Open-error reporting. Accepted rejection/failure returns to the exact retained path for explicit correction/retry and preserves the current project/private input. A changed validation policy rejects at the existing model installation boundary and retains explicit retry. Stale document/private/path/opening ownership retains its existing separate stale-action feedback. Cancel and lifecycle close retire the CPU candidate without applying an earlier Discard decision to private input.

FutureTask observation continues through readiness, so inline delivery followed by handoff failure cannot silently install an unaccepted candidate. An executor fault before acceptance also retires the candidate. Once a result is accepted, it detaches the completed task to avoid interrupting a worker finishing delivery. A later external fault cannot undo consumed replacement. The workflow retires its predecessor before UI completion callbacks; a callback that starts a ready successor and then throws cannot turn the completed replacement into retry or contaminate that successor's path/error/attempt.

Cancellation, failure, staleness, retry and shutdown advance the CPU mailbox epoch and release retained candidates independently of draining callbacks. Retired workers cannot repopulate it. Queued callbacks hold identifiers rather than candidate/diagnostic/failure payloads. Lifecycle close closes the mailbox. Non-cooperative read/compiler cancellation retains its prior limits. Synchronous direct constructors remain synchronous; direct asynchronous owners explicitly accept delivered Open results.

Save/Save As and transition Draft Apply retain their separate completion policies. No file format, schema, registry, public model/engine API or generated field/voxel rule changes. Owner snapshot capture/comparisons, document installation and UI refresh still cost owner-thread work; no measured large-file latency, heap or native/platform bound is claimed.
