# Coherent region progress and summary snapshots

Status: **uncompiled and untested** under the owner development-phase pause. This implements a concurrency/ownership correction for specification 13.5.6 and the existing immutable runtime-result contract. It does not change sampling, generation order, delivery backpressure or acceptance evidence.

Previously StreamingTask.progress read completed/failed counters more than once while the coordinator could advance them. A returned TaskProgress could therefore combine pending computed from one instant with completed/failed from another. Terminal state and cancellation counts were separately visible as well. The individual fields were atomic, but the combined public value was not one count partition.

The region coordinator now owns its mutable completed/failed counters and publishes one volatile immutable TaskProgress whenever its phase or counts change. Readers return that single value without taking locks or reconstructing counts from independently changing fields. Pending, completed, failed and cancelled always partition the effective chunk total within the same snapshot. Retained values do not change, polling allocates no additional snapshot, and later observations cannot move completed/failed/cancelled backward or pending forward. The coordinator observes cancellation cooperatively; requesting cancellation does not pretend unfinished cleanup or acknowledgements have already completed.

PENDING and RUNNING retain pending work. Successful delivery increases completed only after the host acknowledgement succeeds. Delivery/generation failures increase failed under the existing policy. Normal completion, fail-fast, explicit cancellation and context closure publish terminal partitions with zero pending. Fatal failures retain the existing exceptional completion policy and expose a coherent FAILED snapshot. Terminal completion still follows request/region-slot cleanup, and completion observers remain independent copies. Shared chunk ownership, host stages, profiling, priorities, bounded failure details and collection leases retain their existing behavior.

RegionSummary now requires non-null requested bounds, effective Optional and progress, and copies its failure list with List.copyOf. Null lists/elements are rejected at construction. Caller mutation cannot later alter a public summary, its hash/equality or a RegionResult that retains it; the returned failure list is immutable. Failure-detail count remains independently bounded at 1,024 while failed progress continues counting every failed chunk. Public record components and signatures, project/archive/configuration formats and headless dependency boundaries are unchanged.

Eleven deferred RegionProgressTest definitions cover four simultaneous readers across roots 2/4, both delivery orders and success/mixed failure; independent effective clipping counts; empty effective regions; fail-fast; held-acknowledgement cancellation; context close with a healthy peer and retained immutable chunk; fatal consumer outcome; 2,049 failures with 1,024 retained details; mutable-list detachment through RegionResult; a lazy region near signed-long count capacity without eager allocation; and malformed summary ownership. Each full matrix region has an independently known 257 × 2 × 2 = 1,028 chunks, with 512 odd-X delivery failures and 516 successful even-X deliveries. Latches hold actual acknowledgement/read phases rather than relying on generation duration. These definitions have not run.

The existing engine-JAR-only RegionCompletionConsumer now invokes RegionProgressConsumer. Twelve roots/order/outcome cases use two concurrent readers each, retain at most sixteen snapshots per reader, compare monotonic count partitions and exact terminal results, preserve pending host acknowledgements on cancellation, and read 432 retained EMPTY cells after all runtimes close. Two additional lazily cancelled regions use BigInteger expectations above 2^53, including 9,223,372,028,264,841,218 chunks at root 2, to retain every pending/cancelled count bit with only bounded in-flight work. A caller-owned failure list is independently mutated to check summary detachment. The original 1,024 world-cell / 72 retained-cell ownership replay and complete authoring JSON comparison remain unchanged. The new region-completion-progress.json fits the existing manual workflow's independent-client compilation, invocation and artifact glob; no workflow changes or execution are added.

Only source inspection, Java formatting and git diff --check are performed.
