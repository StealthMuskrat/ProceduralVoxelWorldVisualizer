## Current visible controls precede diagnostic publication

Interactive committed-project validation previously replaced diagnostic rows or reported worker failure during queued UI delivery. It now holds the immutable diagnostic list or worker failure in a one-slot CPU mailbox. Delivery marks readiness while retaining RUNNING, the exact request token and previous diagnostic publication. It changes no rows, feedback scope, project/history, separate private Properties input, selection, preferences or runtime engine.

DiagnosticsPanel handles the visible Validation footer's current Start/Cancel, Copy and Go To Problem decisions, unwinds the window scope and accepts only the request shown by those controls. Cancel Validation therefore wins when its release activates on a ready frame. Newly started work, including synchronous completion inside Start, needs a draw that owns that new request before visible acceptance. Escape retains its existing action suppression and additionally defers acceptance on its key-activation frame; it does not become a stop-check command. Use Cancel Validation to stop the check.

Closing or collapsing the results window preserves the prior explicit-background-check policy. Desktop still calls drawValidation each frame; when no Validation content is visible, that path accepts a current ready result after native scopes have ended. Thus hidden/collapsed checks finish without reopening the window or another confirmation. This is distinct from cancelling a private document edit. The existing synchronous EditorState.validateProject path still cancels an outstanding interactive request before publishing directly.

Final acceptance retains document lifetime, committed project identity/revision, complete source values and original diagnostic identity/contents/scope checks. It captures its original request before refresh, so retired work cannot authorize a successor. Private draft, provisional raw text, selection and preference changes remain independent of a committed check. Successful diagnostics publish once and retain immutable rows and exact row-action ownership. Ready status still follows the existing later identity/revision staleness policy; it does not promise repeated full serialization of unchanged frames.

Ready worker failures remain cancellable before reporting. Accepted failure, worker CancellationException, scheduler/external-Future/handoff faults, explicit retry and reporting containment retain their existing recovery. The request retains its FutureTask observation after readiness because an inline handoff may still fail before returning. Inline delivery followed by an executor or handoff fault has not yet published and retires as failure. If a caller explicitly accepts during an inline handoff before that later fault, consumed publication cannot be reclassified. A failure reporter may explicitly start a ready successor; the old acceptance leaves it pending for its own decision.

Cancellation, staleness, closure and replacement clear the CPU mailbox independently of callback draining. Queued callbacks capture identifiers rather than completed diagnostics/failure payloads. Retired workers cannot refill the slot; interruption/removal of running or queued work remains best effort. Owner-thread snapshot capture, complete publication comparisons, diagnostics/event reporting and native projection retain cost. No measured latency/heap, physical input, OS/DPI or complete GUI claim is made. Model/engine public APIs, schemas, registry data, saved formats and field/voxel semantics are unchanged. Other background completion paths retain their separate policies.
